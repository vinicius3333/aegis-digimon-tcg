## Defect found and fixed

### `[Veemon]` was a substring name gate

`compiled.digivolutionRequirement[0]` used `names: ["Veemon"]`. The engine matches `names`
by substring — `apps/api/src/engine/cards/cardData.ts`, `matchGatedRequirement`, comment
"Name gate: base name must contain at least one token (substring)". Every card whose name
contains "Veemon" therefore took the printed `[Veemon]` route for 3 memory, including
`ExVeemon` (BT3-025, Lv.4) and `DemiVeemon`. Because the name route carries no level gate,
this let a Lv.4 base and a Digi-Egg name stand in for a Lv.3 [Veemon].

Fix in `apps/api/src/cards/BT23/BT23-054.ts`: `namesExact: ["Veemon"]`, consumed at
`cardData.ts` "Exact-name gate: one of the base's effective names must EQUAL one token".

Red-then-green proof, test "refuses an illegal source: ExVeemon, a Lv.4 whose name only
CONTAINS Veemon":

- before the fix: `expected { ok: true } to deeply equal { ok: false, reason: "invalid-evolution" }`
- after the fix: passes.

### Checked and NOT a defect

- Zone on the protection filter. A zone-less permanent filter already resolves to the
  battle area only (`targeting/permanents.ts`, `allowsZone` returns `zone === "battleArea"`
  when `filter.zone` is unset), so no `zone: "battleArea"` is needed. Pinned by the
  breeding-area test.
- `nameOrTrait` with `match: "trait"` reads printed forms/attributes/types, so
  `[Royal Knight]` and `[CS]` are whole-token trait identities, not substrings.

## Prior test weaknesses replaced

The previous suite used `advance.fire(EffectTiming.OnPlay, ...)` for the whole On Play body
(structural only), asserted `{ ok: true }` on digivolution without any cost assertion or the
`useAlternateCost` flag, had no illegal-source negative, proved the keywords only through
`hasKeyword`, never exercised return-to-deck, and switched `state.turnSeat` by hand instead
of opening a resolution-source window. The new suite drives `startTurnLoop` + `playCard`,
`digivolve` with and without `useAlternateCost`, `declareBlock`, a real attack for Armor
Purge, and `enterEffectResolution` for the opponent-vs-own controller boundary.

## Remaining gaps

- No Q&A exists for this card, so trait-alias questions (for example whether a granted
  [Royal Knight] trait qualifies a target) are unresolved by ruling; the tests use printed
  traits only.
- ＜Armor Purge＞ is proved on the deletion-by-battle path only. The engine's conformance
  suite already covers the keyword's other entry points, and no BT23-054 clause depends on them.
- The protection is proved against `returnToHand` / `returnToDeck`. The "returned to decks"
  wording also covers security-deck placement; the engine normalizes both into the single
  `beReturned` restriction (`interpreter/actions/restrictions.ts`), and no separate
  security-return verb is exposed to exercise it independently.
