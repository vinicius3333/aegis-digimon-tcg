## Clause -> test -> IR

Clause 1 -> `compiled.effects[0]`: `trigger: "OnDeletion"`, `isInherited: true`, one
`Return` action with `to: "hand"`,
`target.filter: { zone: "trash", controller: "mine", kind: ["Digimon"], colors: ["Purple"], levels: [3] }`,
`count: 1`, and
`condition: { kind: "not", condition: { kind: "triggerRemovalCause", removalCause: "byBattle" } }`.

- `levels: [3]`, `colors: ["Purple"]`, `kind: ["Digimon"]`, `controller: "mine"`,
  `count: 1`, `to: "hand"` — "returns exactly one level 3 purple Digimon from your trash
  after a non-battle deletion". The endpoint is exact: `hand` equals `["BT10-071"]`, your
  trash equals the four remaining cards plus the deleted stack (host BT3-083 and the
  Pagumon, both asserted by instance id), the opponent's trash is untouched, the battle
  area is empty and no decision is left pending.
- `colors` is inclusion, not exact match — "counts a multicolour purple level 3 Digimon
  and still returns only one card": the Green/Purple BT16-040 Wormmon is a legal
  candidate. Two candidates are present; `preferInstanceIds` names the Wormmon so the
  endpoint is deterministic, and exactly one card moves.
- Empty candidate set — "does nothing when your trash holds no level 3 purple Digimon":
  hand stays empty, both trashes are asserted whole, no pending decision.
- `§4-14-1 / §4-14-2` ordering — "can return the host's own card, which reaches your
  trash before the effect resolves": the host BT2-067 DemiDevimon is itself a level 3
  purple Digimon, so after a non-battle deletion of an otherwise-empty board it is the
  only candidate and comes straight back. The endpoint is asserted by **instance id**,
  so it is provably the very card that was just deleted. This is the behaviour the
  rules require and it is now pinned rather than left to chance. (The isolating tests
  above therefore use the Purple **Lv4** BT3-083 Meramon as the host, so the host is not
  a competing candidate.)
- `condition` (`not byBattle`) — "does not fire when the host is deleted by battle": a
  1000 DP suspended BT2-067 host with BT10-071 in trash is attacked by a 5000 DP
  BT1-009 through the public `attack` intent. Nothing is returned even though a legal
  candidate — and the host card itself — is sitting in the trash.

## Peer / stack proof

"carries the return through the real Digi-Egg route: hatch -> digivolve in breeding ->
battle area" exercises the full lifecycle through public intents only:

1. `hatchEgg` moves BT19-006 from the egg deck into breeding (egg deck emptied,
   breeding top card asserted).
2. `digivolve` puts the Purple Lv3 BT2-067 DemiDevimon onto the egg inside the breeding
   area (Purple Lv2, cost 0); the egg instance id is the sole `breeding.stack` entry and
   the battle area is still empty.
3. `moveFromBreeding` on the next own turn carries the stack into the battle area; top
   card and stack identity asserted again.
4. A non-battle deletion of that carrier fires the inherited clause from under the real
   host: exactly one BT10-071 joins the hand (hand grows by exactly one, counted against
   the drawn cards), the three near-miss trash peers stay put, the opponent's purple Lv3
   in their own trash is untouched, and the battle area is empty.

Near-miss peers appear on four axes (level, colour, kind, controller) plus the
multicolour positive and the battle-deletion negative.

## Defects

None in the module. The IR was correct on the single printed clause, including the
`levels: [3]` gate and the `not byBattle` condition.

The **pre-existing test** is replaced. Its weaknesses:

- Its positive assertion was `hand).toContain("BT10-071")` plus
  `trash).toEqual(arrayContaining([...]))` — neither pins how many cards moved. Its
  host BT19-067 Impmon is Purple Lv3 and so is itself a legal candidate, and its trash
  peer BT19-069 Deltamon is Purple/Black Lv4; the test would have passed had two cards
  been returned, or had the host come back instead of the Gazimon.
- Its host BT19-067 carries an `[On Play]` effect of its own, so the fixture is not
  attributable to BT19-006 alone.
- No test for the multicolour case, the controller gate, the "no candidate" case, or
  the §4-14-2 ordering question the card's own host raises.
- No lifecycle: BT19-006 appeared only as a seeded `under:` entry.

No red tests retained. No engine gap found.

## Remaining gaps

- The clause says "return 1", which is mandatory when a candidate exists. The tests run
  with `autoAcceptOptional: true`, so a hypothetical regression that made the effect
  optional would still pass. Proving mandatory-ness would need an `autoDeclineOptional`
  run asserting the card returns anyway; not added, because the IR carries no `optional`
  flag to regress against and the decline path would be answering a prompt that is
  never raised.
