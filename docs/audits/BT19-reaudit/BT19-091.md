names). No other divergence between catalog and errata.

## Clause -> test -> IR

- **Clause 1 (colour waiver)** -> `effects[0]`: `trigger: "Static"`, single
  `WaiveColorRequirement` on `filter.isSelfRef`, gated by
  `youHave { levels: [5], nameOrTrait: [{ tokens: [WarGrowlmon, Taomon, Rapidmon],
  match: "nameExact" }] }`. This is the accepted `isColorWaiverStatic` shape
  (`interpreter/effect.ts:336`, `builders.ts:490`).
  - Proven through real `playCard` intents: refusal (`color-requirement-unmet`,
    memory untouched, card still in hand) on an all-blue board, on one, two of the
    three colours, on a Lv.5 BlackWarGrowlmon and on a Lv.5 Monzaemon; acceptance
    (cost 8 charged: memory 10 -> 2, Option in trash) on all three colours, on
    BT10-055 Green/Yellow + BT1-013 Red (CR 4-22-4) and on the Lv.5 purple
    [WarGrowlmon] with no matching colour at all.
- **Clause 2 (three tokens)** -> `effects[1].actions[0..2]`: three `PlayToken`
  actions, one per token, each gated `not youHave { kind: ["Digimon"],
  nameOrTrait: [{ tokens: [<name>], match: "nameExact" }] }`.
  - Board endpoints: `TOKEN-WarGrowlmon-Token` / `TOKEN-Taomon-Token` /
    `TOKEN-Rapidmon-Token`, `currentDP` and `baseDP` 6000, empty `stack`,
    controller seat 0, `effectiveColors` Red / Yellow / Green, definition `level`
    `undefined`, `playCost` `-1`, `isToken: true`.
- **Clause 2 (＜Alliance＞ twice, then attack)** -> `effects[1].actions[3]`
  `GainKeyword { keyword: Alliance, count: 2, duration: "forTheTurn",
  target.filter { controller: mine, kind: [Digimon], levels: [5], excludeToken } }`
  and `actions[4]` `Attack { sameTarget: true, mandatory: true }` over the same
  filter. `count: 2` produces two ledger grants, which is exactly what
  `GameEngine.allianceCount` (line 973) reads to open a second prompt — the engine
  comment at `interpreter/actions/board.ts:483-487` cites this card by name.
  - Endpoints: the Lv.5 host carries the grant; the Lv.3 red peer, the Lv.4 yellow
    and green peers and all three tokens do not. The host attacks, two
    `alliancePrompt` events fire, two allies end suspended, the host ends
    suspended, and the defender's security drops by exactly 3 (1 base check + 1
    per ＜Alliance＞ instance).
- **Clause 3 ([Security])** -> `effects[2]`: `PlayWithoutCost` from `hand`,
  `optional: true`, `payCost: false`, filter `levels: [5]` + the same
  `nameExact` name set.
  - Proven through a real security check: seat 0 declares `attack` at
    `{ kind: "player" }` into a security stack topped by BT19-091. BT3-052
    (Lv.5 Green Rapidmon, printed play cost 6) lands on seat 1's battle area, no
    memory of that size moves, and BT19-091 goes to seat 1's trash. With only
    BT16-101 (Lv.6, name `Rapidmon (X Antibody)`) and BT5-079 (Lv.5
    BlackWarGrowlmon) in hand, nothing is played and both stay in hand.

## Remaining gaps

- The brief asked for "acceptance with each single colour". That premise is wrong
  for a multicolour Option: CR 4-22-3 requires **all** of the card's colours, and
  the engine implements it (`GameEngine.printedColorRequirementMet`, `required.every`).
  The tests assert the refusal for each single colour and acceptance only on the
  full set, plus the CR 4-22-4 multicolour-source case.
- The engine's effect-driven `Attack` chooses the attack target inside `forceAttack`;
  the tests seed an opponent with no Digimon so the attack necessarily goes to the
  player. The "must attack if possible" wording of Q3163 (i.e. that the controller
  cannot decline the attack itself) is proven only in that the attack happens with
  no decline prompt offered.
- ＜Alliance＞ prompts have no `setupEngine` flag; the tests answer them through an
  `onEvent` responder that replies with `respondAlliance`. Worth a harness
  affordance, but out of this lane's allowed edits.
