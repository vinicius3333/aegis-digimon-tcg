## Name / trait semantics — checked, not assumed

The printed gate is "with `[Aqua]`/`[Sea Animal]` **in one of its traits**", which is
the SUBSTRING form (the exact form is "with the [X] trait"). The IR uses
`nameOrTrait: [{ tokens: ["Aqua", "Sea Animal"], match: "traitContains" }]`, which is
the right key: `interpreter/matching/definition.ts:365` implements `traitContains` as
`traits.some(x => x.includes(token))` after `normalizeTrait` lower-cases and strips
whitespace and hyphens.

Consequences, confirmed against the catalog's actual trait vocabulary
(`Ancient Aquabeast`, `Aquabeast`, `Aquatic`, `Sea Animal`, `Sea Beast`):

- `"aquatic"` and `"aquabeast"` both contain `"aqua"` -> both QUALIFY. There is no
  trait literally named `Aqua`, which is why the printed wording is the substring
  form at all.
- `"seabeast"` does not contain `"seaanimal"` and contains no `"aqua"` -> [Sea Beast]
  does NOT qualify. This is the near-miss the brief called for, and it is now a real
  assertion rather than an argument.

Engine limitation noted while reading the seam, NOT a defect of this card: the
live-permanent path that unions continuously GRANTED traits into a trait predicate
(`interpreter/matching/permanent.ts:683-697`) only handles `match: "trait"`, not
`match: "traitContains"`. A trait granted at runtime would therefore be invisible to
this clause. It does not bite here because every qualifying trait in these fixtures is
printed in `cards.json` (including BT19-027's [Aquatic], see the discrepancy section).
Flagged for the coordinator as an engine-wide seam, not fixed from this lane.
