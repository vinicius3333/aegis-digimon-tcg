## Intermittent timeout — cause and fix (session 3, lane C3)

Symptom: `treats [Matt Ishida] as a substring of the Tamer name` timed out at 15 s in about
one run in two, but only when `BT17-catalog-sync.test.ts` ran earlier in the same worker.

Reproduction (3 runs):

```
pnpm --filter @aegis/api exec vitest run src/cards/BT17/BT17-catalog-sync.test.ts \
  src/cards/BT17/BT17-019.test.ts src/cards/BT17/BT17-007.test.ts \
  --maxWorkers=1 --no-file-parallelism
run 1 -> 2 failed | 129 passed (BT17-019 + BT17-007 timeouts, 31.1 s)
run 2 -> 131 passed (0.75 s)
run 3 -> 1 failed | 130 passed (BT17-019 timeout, 15.7 s)
```

Cause: the fixture puts `BT17-081` "Tai Kamiya & Matt Ishida" on the board purely as a
catalog-identity peer. The catalog-sync file imports every BT17 module, so in a shared worker
`BT17-081`'s own compiled effects are registered too and raise an optional "use this effect?"
prompt during `advance().runTurn(0)`. The test set no decision automation flags, so nothing
answered the prompt and the turn loop waited out the 15 s timeout. It is registration order,
not timing: alone the module is never registered and no prompt exists.

Fix: pass `{ autoDeclineOptional: true, autoSelectCards: true }` to `setupEngine`. Declining
leaves the asserted flow untouched — BT17-019's `[Start of Your Main Phase] ＜Draw 1＞` is
mandatory — so the endpoint assertions (hand +1, deck empty) are unchanged and unweakened.
No `it.skip`, no timeout bump.

Result: 6 consecutive green runs of the trio, all ~0.6 s, no 15 s stall.
