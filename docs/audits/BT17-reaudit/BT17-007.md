## Intermittent timeout — cause and fix (session 3, lane C3)

Symptom: `counts a Tamer with [Tai Kamiya] inside a longer name but not a different Tamer`
timed out at 15 s intermittently, but only when `BT17-catalog-sync.test.ts` ran earlier in the
same worker.

Reproduction (3 runs):

```
pnpm --filter @aegis/api exec vitest run src/cards/BT17/BT17-catalog-sync.test.ts \
  src/cards/BT17/BT17-019.test.ts src/cards/BT17/BT17-007.test.ts \
  --maxWorkers=1 --no-file-parallelism
run 1 -> 2 failed | 129 passed (BT17-007 + BT17-019 timeouts, 31.1 s)
run 2 -> 131 passed (0.75 s)
run 3 -> 1 failed | 130 passed (0.6 s for BT17-007)
```

Cause: the peer/stack section above assumed `BT17-081` is never imported, so only its catalog
identity is in play. That holds when the file runs alone. `BT17-catalog-sync.test.ts` imports
every BT17 module, so in a shared worker `BT17-081`'s compiled effects are registered and raise
an optional prompt during `advance().runTurn(0)`. With no decision automation flags set nothing
answered it and the turn loop hung to the 15 s timeout.

Fix: pass `{ autoDeclineOptional: true, autoSelectCards: true }` to that fixture's
`setupEngine`. Declining does not touch the asserted clause — BT17-007's
`[Start of Your Main Phase]` return-from-trash is mandatory — so the endpoints (WarGreymon in
hand, trash empty) stand unchanged. No `it.skip`, no timeout bump. The peer claim itself is
unaffected: the substring gate still has to accept "Tai Kamiya & Matt Ishida" and reject
"Matt Ishida".

Result: 6 consecutive green runs of the trio, all ~0.6 s, no 15 s stall.
