## Defects found and fixed (both are IR changes)

### 1. `[Your Turn]` DP aura wrongly gated on controlling a Tamer yourself

The aura carried a `while` gate `{ kind: "youHave", filter: { controllerDefault:
"mine", kind: ["Tamer"] } }`. `runStaticAction` (`apps/api/src/engine/effects/
interpreter/actions/statics.ts:24`) treats `while` as a hard gate: if false the whole
aura returns without applying. But the aura's own `scaling.filter` is `controller:
"any"` (counts both players' Tamers), matching the printed bare "For each Tamer" and
the predecessor BT6-086 "For each Tamer in play". So the module was self-contradictory:
it scaled by every Tamer in play yet suppressed the entire bonus whenever you did not
control a Tamer. On your turn with an opponent-only Tamer, your Eosmon received +0
instead of +1000.

The prior audit (`internal-docs/audits/BT17/BT17-071-080.md`) corrected the *scaling*
filter to `any` but left this `while` gate at `controllerDefault: "mine"` — an
overlooked residual defect.

Fix: removed the `while` gate. The printed text carries no "if you have a Tamer"
condition; with 0 Tamers the scaling already yields +0, so no gate is needed. The
battle-area guard stays implicit (no source permanent → no candidates).

Proof: `boosts your Eosmon by an opponent-only Tamer on your turn` — seat 0's turn,
seat 0 has only the Eosmon, seat 1 has one Tamer (BT17-088). `currentDP` is 13000.
Pre-fix this asserted 12000.

### 2. Digivolve route must be `namesExact`, not `names`

Printed `[Digivolve]Lv.5 [Eosmon]: Cost 4` has no "in name", so per the coordinator
route-name decision the requirement must use `namesExact` (exact) rather than `names`
(substring). Changed `digivolutionRequirement[0].names: ["Eosmon"]` →
`namesExact: ["Eosmon"]`. `cardData.ts:487` reads `namesExact` as an equality gate.

Note: the brief also asks for a near-name substring negative (a card whose name
contains "Eosmon" but is not exactly "Eosmon", refused). No such card exists — all
seven Eosmon-named cards (BT6-083/085/086, BT7-084, BT17-074/075/076) are named
exactly "Eosmon". So `namesExact` vs `names` is not behaviorally observable in the
current pool; the change is correctness-only. The name gate is still guarded by a
Lv5 non-Eosmon negative (BT1-024).

## Q&A coverage (Q2844, Q2845, Q2846)

- **Q2844** (this card's own play triggers its `[All Turns]` deletion): covered by
  `triggers its own [All Turns] deletion when this Eosmon is played (Q2844)`. Hard-play
  BT17-076 (itself an Eosmon) → its `whenPlayed` subtrigger fires on itself and deletes
  an opponent Digimon (BT17-063 dp 6000 ≤ 12000). No engine seam here; the subtrigger
  catches the play that placed the source.
- **Q2845** (played Eosmon's DP changes before this effect processes → threshold uses
  the processing-time DP) and **Q2846** (played Eosmon removed before this effect
  processes → no deletion): documented untestable in the current harness. Both require
  a *second* simultaneous trigger ordered ahead of this deletion (one that raises, or
  removes, the played Eosmon) in a minimal fixture; no such co-triggering card is
  available to seed cleanly. The IR mechanism is consistent with both rulings: the
  deletion binds the played Eosmon via `SelectBind` (`bindAs: "playedEosmon"`) and the
  `Delete` filter reads `relativeTo: { attr: "dp", op: "lte", selectionRef:
  "playedEosmon" }` live at resolution — so a DP change resolves against the live value
  (Q2845) and a removed reference yields no comparable DP and no legal target (Q2846).
