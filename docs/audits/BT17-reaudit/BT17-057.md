## Defect fixed locally (IR change)

The DigiXros recipe was authored as a single impossible material:
`materials:[{names:["Machinedramon"],traits:["Cyborg"]}], count:1`. No card named
Machinedramon carries the [Cyborg] trait (all are Lv.6 Machine), so the recipe could never be
satisfied, and it dropped the second slot and the level constraint. The printed header
`[DigiXros -2] [Machinedramon] x 1 Lv.5 Digimon card w/[Cyborg] trait` is two slots — compare
BT19-063 `[DigiXros -2] [SkullKnightmon] x [DeadlyAxemon]` ->
`materials:[{names:["SkullKnightmon"]},{names:["DeadlyAxemon"]}], count:2`. Corrected to:

```
materials: [{ names: ["Machinedramon"] }, { level: 5, traits: ["Cyborg"] }], count: 2
```

Behavioural test confirms both materials place and cost drops by 2 (memory 20->10).

IR changed: YES. `packages/shared/src/effects/effects.json` still holds the old single-slot
recipe, so `BT17-catalog-sync.test.ts` will be RED until the coordinator runs the set sync.
`effects.json` and the catalog were not edited (not allowed).

## Retained red (engine seam)

`it.fails` — `accepts a trash card as DigiXros material while a black Tamer is in play
(Q2811)`. The direct `playCard` DigiXros validator
(`apps/api/src/engine/actions/digiXros.ts`, `validateDigiXros`/check, `trashMax` gate ~L203)
recognizes trash materials only via the hand-authored `DIGIXROS_TRASH_NAME_ALLOWANCES` table
(`packages/shared/src/effects/data.ts`) and the `wouldBePlayed AllowDigiXrosMaterialsFromTrash`
IR. It never consults the per-seat `expandDigiXrosZones` ledger that BT17-057's Static
`digixrosFromTrash` grant populates while a black Tamer is in play; that ledger is read only on
the effect-driven play path (`interpreter/actions/play.ts:645`). BT18-065 (same grant shape)
works only because it has an entry in the shared name-allowance table. Expected `{ok:true}`
with the trash Machinedramon placed underneath; actual `{ok:false, reason:"invalid-material"}`.
Fixing correctly needs either a shared-data entry for BT17-057 (shared is not editable in this
lane) or the validateDigiXros path to consult the seat ledger (engine change, not allowed).

## Engine lane E2 resolution (session 3) — retained red CLOSED

Two halves, both engine-side. `validateDigiXros` never read the per-seat
`expandDigiXrosZones` ledger that the effect-driven play path already consumes, so the
direct DigiXros verb was stricter than the effect path; and the ledger was empty anyway,
because BT17-057's Static was routed through `staticModifier`'s on-field base guard while
the permission is only ever read from HAND. `isDigiXrosZoneStatic` now routes that shape to
a guard-free `digiXrosZoneStatic` builder, `runGrantStatic` records an off-field grant
through `expandDigiXrosZonesForPlay` scoped to that card's own play, and `validateDigiXros`
reads the ledger with the same quota rule `play.ts` uses.

`pnpm --filter @aegis/api exec vitest run src/cards/BT17/BT17-057.test.ts --maxWorkers=1 --no-file-parallelism`
red `Tests 14 passed | 1 expected fail (15)` -> green `Tests 15 passed (15)`.
