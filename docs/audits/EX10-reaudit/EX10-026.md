## Defect found and fixed

**＜Save＞ placed the card at the top of the Tamer's stack, not the bottom.**
`runPlaceUnder`'s self/Save branch calls `relocateByEffect(..., { belowTop: action.position !== "bottom" })`.
The compiled IR carried no `position`, so `belowTop` defaulted to true and `pushOnStack`
appended the card — `Permanent.stack` is bottom-first, so the saved card landed directly beneath
the Tamer instead of under the existing cards. Comprehensive Rules 4-3 (and 16-21-6 for the
＜Material Save＞ analogue) require the bottom.

Fix: `position: "bottom"` on the OnDeletion `PlaceUnder` action in `EX10-026.ts`.

Revert check (`docs/audits/EX10-reaudit/logs/EX10-026-revert-check.log`): with the line removed,
the Save test fails with `expected [ 'inst-6', 'inst-3' ] to deeply equal [ 'inst-3', 'inst-6' ]`.
With it restored, all 10 tests pass.

Coordinator note: **this is systemic.** Every ＜Save＞ card in the repo compiles the same
positionless `PlaceUnder` (`BT10-020`, `BT10-021`, `BT10-075`, `BT11-015`, `BT11-077`,
`BT12-008`, `BT12-086`, `BT14-057`, `BT14-059`, `EX4-016`, `EX4-018`, `EX10-015`, `EX10-027`,
`EX10-039`, `EX10-044`, `EX10-045`, …). Only EX10-026 is fixed here; the rest need either the
same per-card edit or a compiler/interpreter default (the cleanest seam would be defaulting the
Save keyword's PlaceUnder to `position: "bottom"`).

## Remaining gaps

- **Q5080's name branch is not reachable for this card.** The gate only inspects Lv.3 bases, and the
  catalog holds no Lv.3 Digimon whose name (or trait) contains "Knightmon" — the only four Lv.3
  candidates (`BT7-057`, `BT10-058`, `BT18-058`, `BT19-055`) all carry it in `effectText`. The
  requirement-line branch is likewise unreachable at Lv.3. Both are covered by code reading
  (`matchGatedRequirement`'s text union) but not by a behavioural test from this card. The
  DigiXros case does prove the reverse direction — EX10-026's own name is matched exactly as the
  `[SkullKnightmon]` material — so the name axis is exercised, just not through clause 1.
- The `[On Play]` and `[When Digivolving]` clauses are two independent IR effects with identical
  bodies. Nothing proves they cannot both fire from one event; a single card cannot be both played
  and digivolved, so this is a structural duplication rather than an observable risk.
- No test asserts what happens when the controller accepts the optional condition with **no** legal
  delete target. 15-7-4 lets a player pay a condition whose follow-up cannot execute, and the KB has
  no ruling specific to this card, so the endpoint is left unasserted rather than guessed.
