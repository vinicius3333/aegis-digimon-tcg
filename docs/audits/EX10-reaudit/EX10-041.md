## What changed

The previous test file proved `[On Play]`, `[When Digivolving]` and the deck watcher with
injected timing (`advance.fireForPermanent(EffectTiming.OnPlay, …)`,
`advance.verb.trash(…)`), which the brief scores 0 in the Behavior column, and it proved
clause 1 and clause 4 only as seeded IR / a hand-laid `under:` stack. It also covered
neither half of Q5122's negative.

The rewritten file drives every clause through public intents: `playCard`, `digivolve`
(with `useAlternateCost`), `attack`, and the real `startTurnLoop()` / `runTurn`. No
`advance.fire*` call remains. The only Advance-Surface calls left are the turn drivers
(`waitForMainPhase`, `endMainPhaseIfOpen`, `runTurn`), which the brief treats as the real
turn loop. Nothing reaches `engine.continuous`, `engine.ledger` or `engine.primitives`;
all reads go through `observe()`.

## Defects found

None in the module. Three things I expected to be wrong and proved were not:

1. **Duration of clause 2.** Reading `ContinuousEffectLedger.sweep` in isolation
   (`keywordGrants` expires via `ownerSeatOfPermanent`, i.e. the RECIPIENT's controller)
   suggested `untilOpponentTurnEnd` on a grant placed on an opponent's Digimon would clear
   at the controller's own turn end, which would make the clause useless. The behavioural
   test through the real turn loop shows the opposite: the grant survives seat 0's turn
   end, is live during seat 1's whole turn, and is gone at seat 0's next Main. The sweep
   seat is the seat whose turn just ended and the ledger's naming is controller-relative
   after all. `untilOpponentTurnEnd` is correct and matches the repo convention
   (BT21-043, BT22-031, BT23-025, BT23-050 all encode "until their turn ends" the same way).
2. **Q5122 by construction.** The module comment claims both clauses are effect-only by
   construction. Verified: `fireWhenTrashedFromDeck` has exactly three call sites
   (`actions/resources.ts` TrashTopDeck, `actions/removal.ts` deck-zone trash, `costs.ts`
   deck cost), all direct-from-deck; `RevealAdd`'s `rest: "trash"` disposal calls none of
   them. `OnDiscardSecurity` is fired per instance from `fireDiscardedFromSecurity`, which
   only the effect-driven security-trash seams call. Both negatives now assert this
   behaviourally rather than trusting the comment.
3. **`OnDiscardSecurity` scoping.** It fires via `fireTimingForInstance`, so it is
   self-scoped; it cannot fire off another player's or another card's security trash.

## Remaining gaps

- No test for the zero-opponent-Digimon case of clause 2 (a mandatory "give 1" with no
  legal recipient). Low risk: `resolvePermanentTargets` returns an empty set and the
  action is a no-op.
- The Q5122 negative for the *security* half uses an ordinary security check. I found no
  implemented card that reveals cards from a security stack and trashes them, so the
  "revealed from the security stack" wording is covered by the check path plus the
  construction argument above, not by a reveal-from-security effect.
