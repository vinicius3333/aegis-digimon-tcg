## Knowledge-base check

`node tools/kb/query.mjs card EX13-021` → `(no knowledge-base entries)`. **No KB rulings
available; the set is pre-release.** General rules consulted in `data/kb/rules/comprehensive.md`:

- **§4-23-1 / §4-23-2 / §4-23-3** — cards "with XX in their texts". "In its text" is scoped to the
  information printed on *that* card, and gaining an effect is explicitly **not** gaining the text
  (§4-23-2's own example: a digivolution card whose inherited effect prints ＜Save＞ does not give
  its host ＜Save＞ text). This is what makes clause 6's host gate a retained red — see below.
- **§4-24** — "XX/YY" means "XX or YY", confirming the single OR-union reading of
  `[Dracomon] or [Examon]`.
- **§15-3** — inherited effects are effects of the Digimon that gained them, regardless of which
  digivolution card they came from (this is the rule the engine's over-wide text union conflates
  with §4-23).
- **§15-7-1 / §15-7-2** — only an explicit "by X, Y" *optional processing condition* gates the text
  that follows it. Clause 3 is a mandatory trash with no "by", so clause 4 is **not** payment-gated.

### Notable modelling decisions

- **`fromTop: false` is what makes it the bottom slice.** `runTrashDigivolution`
  (`apps/api/src/engine/effects/interpreter/actions/placeUnder.ts`) walks `stack` from index 0 —
  bottom-first — when `fromTop` is false. `Permanent.stack` holds only the cards beneath the top
  card, so the seeded order is the printed order.
- **`namesExact` for `[Coredramon]`.** The bracketed reference is literal card-name equality, so
  every printing named exactly "Coredramon" qualifies and "Coredramon X"-style relatives do not.
  Because the header carries no color, it is strictly wider than the catalog EvoCost on one axis (a
  green Coredramon reaches this card for 3) and narrower on another (a blue Lv.4 that is not a
  Coredramon still pays 4). Both directions are proven.
- **`blocksCombatSuspend: true`.** `restriction: "suspend"` alone normalizes to the effect-facing
  `beSuspended`; without the flag the opponent could still declare an attack with the locked
  Digimon, which is the exact thing the clause exists to stop. BT26-031 and EX11-017 pair the two
  for this wording.
- **No `ifThisEffectActed` on clause 4.** Per §15-7-2, only a "by X" optional processing condition
  gates what follows "Then". EX11-017, whose printed sentence is nearly identical ("trash any 3
  digivolution cards from your opponent's Digimon. Then, 1 of their Digimon … can't suspend until
  their turn ends"), is modelled the same way. BT26-031's guard exists only because its first half
  *is* a "By trashing …" cost.
- **`hostFilter`, not `sourceFilter`, for clause 6's host gate.** `sourceFilter` describes the event
  *subject*, and for an inherited effect `isSelfRef` resolves against this card's own definition —
  whose inherited text literally contains "[Dracomon] or [Examon]", so the gate would be vacuously
  true. `hostFilter` re-checks the anchor permanent (`hostFilterGate` → `permanentMatchesFilter`).
- **Peer alignment.** This card is the Blue/Red sibling of BT20-025 Wingdramon, which prints the
  same `[Digivolve] [Coredramon]: Cost 3` header and the same Lv.6 `[Slayerdramon]` clause;
  BT20-042 Groundramon carries the `[Breakdramon]` twin. Both grants are those modules' accepted
  shape verbatim.

## Coordinator correction (post-review)

The worker's original submission misdiagnosed the `match: "text"` host gate as an engine
gap and shipped it as `it.fails`/`coverage: "partial"`. It is not a gap: `hostFilter` accepts
the same `printedTextOnly: true` flag already used by `LM-012.ts` (and independently
rediscovered by the EX13-024 lane for an equivalent filter), which scopes the match to the
host's own printed information instead of also folding in its digivolution-stack inherited
text. The coordinator added `printedTextOnly: true` to `unsuspendHostOnSuspend.hostFilter`,
flipped `coverage` to `"full"` with an empty `residual`, and turned the retained-red test into
a plain passing `it`. All 13 tests now pass with zero expected failures. See
`docs/audits/EX13-authoring/REVIEW-NOTES.md` for the general note on this pattern.

No new engine primitive was needed for any clause.

## Remaining ambiguity

- **Clause 3's target pool.** The printed text says "1 of your opponent's Digimon" with no
  "with digivolution cards" qualifier, so a source-free Digimon is a legal choice and the mandatory
  trash then simply does as much as it can. The filter is left unqualified to match the print
  (BT20-042's plain opponent filter); EX11-017 adds `digivolutionCards: "hasAny"` only because its
  own printed text narrows the pool. Should a ruling later say the controller must pick a Digimon
  that can supply two cards, add the qualifier.
- **Clause 4's independence.** "Then, 1 of their Digimon or Tamers" is read as a fresh, independent
  choice (proven: the lock lands on a permanent other than the trash target). No pre-release ruling
  confirms whether the same Digimon may be picked twice; nothing in the IR forbids it.
- **Clause 6 and the over-wide text union.** Once the engine narrows `match: "text"` on live
  permanents to printed card information, the open question becomes whether a *host whose own
  printed inherited text* carries the token qualifies — §4-23-3 says yes (text counts even when the
  effect cannot be activated), which the current `matchNameOrTrait` union already honours.
