Printed clauses:

2. `Then, delete 1 of your opponent's Digimon with a play cost of 3 or less.`
3. `For each one this effect returned, add 1 to this effect's play cost maximum.`

## Knowledge-base check

`node tools/kb/query.mjs card EX13-053` → **no rulings available; set is pre-release**
(EX13's street date is 2026-10-02 and the local KB holds no EX13 entries).

General rules consulted in `data/kb/rules/comprehensive.md`:

- §4-22-1 — a token "in its text" means anywhere in the card's printed information, which is
  why the return filter uses `match: "text"` (name ∪ traits ∪ every printed text field).
- §16-12-1 — ＜De-Digivolve＞ trashes cards from the chosen stack starting with the top card.
- §15-7 / §15-7-2 — optional processing *conditions* are the "by X, Y" form. This card's
  "You may return …" is a plain optional effect, not a condition, so the following "Then,
  delete …" still resolves when the return is declined. Recorded as the deliberate reading
  below.
- §2-3-1 / §4-22 — card names, which the `[Rule]` clause widens.
- `node tools/kb/query.mjs rules "top of the deck"` → manual §1 only covers the order of
  *revealed* cards returned to the deck. The printed clause says nothing about order, so the
  encoding carries no `order: "any"` (BT8-065, which does print "in any order", is the card
  that would).

## Findings worth recording

1. **A `match: "text"` proof cannot use BT8-061 Thundermon as its "text-only" fixture.**
   `matchNameOrTrait` folds `effectiveStaticNames(def)` into the `names` list
   (`apps/api/src/engine/effects/interpreter/matching/definition.ts:331`), so a card whose
   printed line says "also treated as [X]" already answers a `match: "name"` filter from its
   definition alone — no live permanent needed. A text-only discriminator therefore needs a
   card that merely *mentions* the token (EX13-046 Kokuwamon here). Not a gap; a fixture trap
   that silently makes a `"text"` vs `"name"` mutation test look inert.
2. **This card can return itself.** Its `[On Deletion]` resolves with the card already in the
   trash, and its own printed text contains `[Mamemon]`, so it is a legal return target and
   counts toward the play-cost maximum. Asserted explicitly in the `[On Deletion]` test
   (3 returns including itself ⇒ a maximum of 6). This follows from the printed text; no
   ruling exists to contradict it pre-release.

## Engine gaps

**None.** Two candidates were checked against REVIEW-NOTES.md and the engine before being
dismissed:

- *Scaling the delete's play-cost ceiling.* `DeleteAction.playCostCeiling` narrows `unit` to
  `"cards" | "digivolutionCards"` and cannot read a context count — but
  `Filter.playCostLteScaling` can, and `runAction.ts:341` explicitly recognizes it on a
  `Delete` target (`dynamicallyScaledDeleteTarget`). One-field fix, not a seam.
- *`printedTextOnly`.* The REVIEW-NOTES "text self-match" trap does not apply: the candidates
  are loose trash cards with no digivolution stack, so there is nothing for the flag to
  narrow.

## Remaining ambiguity

- **"Then," after an optional sentence.** Read as: the delete resolves regardless of whether
  any card was returned (§15-7-2 governs "by X, Y" processing *conditions*, which this is
  not), and clause 3's "for each one this effect returned" is written to cover the zero case.
  The card's own numbers support this — base 3 rising to 6 — and BT14-098, which *does* gate
  its deletion on the same return, prints the "by returning …" cost form instead. A later
  ruling that gates the delete would be a one-field change (`abortOnDecline: true` on the
  `Return`).
- **Order of the returned cards on the deck top.** The clause prints no choice, so none is
  offered. If a ruling grants the controller the order (as manual §1 does for *revealed*
  cards), the fix is `order: "any"`.
