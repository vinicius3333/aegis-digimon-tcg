Printed clauses:

1. `[When Moving] [On Play] Reveal the top 3 cards of your deck. Among them, add 1 card with
   [Sukamon] or [Etemon] in its name to the hand and trash 1 such card. Return the rest to the
   bottom of the deck.`
2. `[Inherited] [All Turns] [Once Per Turn] When this Digimon would leave the battle area other
   than by your effects, by deleting 1 other Digimon with [Sukamon] in its name, it doesn't
   leave.`

No `[Digivolve]` header, no security effect, no Ace/Link/Dual fields. Both evolution routes are
plain catalog EvoCosts, so the module carries no `digivolutionRequirement`.

### Filter-discrimination fixtures

The "in its name" reference is proven to discriminate rather than merely fire, with three
same-archetype fixtures:

- `BT3-063` Sukamon, `BT3-070` Etemon — exact tokens.
- `BT13-065` PlatinumSukamon — **substring** match, which is why the reference is `match: "name"`
  and not `nameExact`.
- `BT11-063` Geremon — the near-match: it prints `[Sukamon]` inside its own effect **text** but
  not in its name, so a `match: "text"` encoding would wrongly accept it.
- `BT3-061` Chuumon — plain archetype non-match.

The inherited cost adds a second discrimination axis: `[Etemon]`-named cards are refused there,
because that clause names only `[Sukamon]`.

## Peer consistency

- Reveal-and-trash shape: `BT24-066` prints the identical "add 1 … to the hand and trash 1 such
  card" sentence; this module reuses its two-slot encoding verbatim (plus `requiresMinRevealed`).
- Two-timing single sentence: `EX13-007`, `EX13-008` (same set) — two effects sharing one action
  list.
- `[Sukamon]`/`[Etemon]` name reference: the Chuumon siblings `BT13-062` and `EX5-045` both use
  `match: "name"` with the same tokens.
- Leave replacement: `EX11-022`, `EX13-015` for the modern `Replacement` + `deleteOwn`-cost shape;
  `BT11-040` and `BT13-065`, the two earlier cards printing the very same "1 other Digimon with
  [Sukamon] in its name" sentence, for the `controller: "any"` + `excludeSelf: true` cost target.

## Mutation checks (proof that the IR fields are load-bearing)

Each mutation was applied to the module, the suite re-run, and the module restored:

| Mutation | Behavioural test that failed |
| --- | --- |
| `match: "name"` → `"text"` | substring test, no-match test |
| `controller: "any"` → `"mine"` | opponent-pays-the-cost test |
| drop `excludeSelf` | host-cannot-pay-for-itself test |
| drop `leaveCause` | own-effect test |
| drop `frequency: "OncePerTurn"` | once-per-turn test |
| drop `requiresMinRevealed: 2` | **none** (see below) |
| drop `oncePerTurnKey` | **none** → the field was removed |

Two honest notes from that run:

- `requiresMinRevealed: 2` on the trash slot changes no observable behaviour in this engine: the
  hand slot already consumes the only match, so the trash slot finds nothing regardless. It is
  kept for parity with `BT24-066` and the comment says so.
- `EX13-015` carries both `frequency` and a redundant `oncePerTurnKey` on its leave replacement.
  Here `frequency` alone is what the interpreter budgets, so the key is left off rather than
  shipped as an unproven field.

## Retained reds

None. `coverage: "full"`, `residual: []`. No engine seam was hit: every primitive this card needs
(`RevealAdd` with a trash slot, `Replacement`/`wouldLeavePlay` with a `deleteOwn` cost) already

## Remaining ambiguity

"by deleting **1 other Digimon** with [Sukamon] in its name" omits "of your", unlike the
`EX13-048` / `EX13-052` wording in this same set ("1 of your other Digimon"). Read literally the
cost may be paid from either side of the board, which is how the two earlier prints of this exact
sentence (`BT11-040`, `BT13-065`) are already encoded, so this module follows that precedent with
`controller: "any"` and a test that pins it. If a post-release ruling narrows it to the
controller's own Digimon, the fix is a one-word change to `controller: "mine"` and the
`may pay the cost with the opponent's [Sukamon]-named Digimon` test inverts.
