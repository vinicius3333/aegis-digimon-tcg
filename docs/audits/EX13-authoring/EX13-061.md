## Notable readings

- **C1 is behaviourally separable here**, unlike its EX13-014 Jesmon sibling: the alternate header
  (cost 4) is CHEAPER than the catalog EvoCost (Black Lv.5 for 5) and colour-blind, so a red Lv.5
  `[Huckmon]`-text base (ST12-08) charging 4 can only have come from the header, and a black Lv.5
  without the token (BT10-064) charging 5 can only have come from the EvoCost.
- **C2 is one unlevelled slot of three, not three levelled slots.** The printed header names no
  level, so three Lv.3 materials with distinct names are legal — proved directly, and it is the
  deliberate structural difference from EX13-014's `Lv.5 × Lv.4 × Lv.3` header.
- **C6 uses `Restrict`/`beAffected`, not `GrantImmunity`.** `GrantImmunity`'s
  `immuneFrom: "opponentEffects"` blocks every opponent effect; the printed sentence says "their
  DIGIMON effects", so the EX12-019 encoding (`fromSourceKind: ["Digimon"]` +
  `byOpponentEffectsOnly: true`) is the precise one. Proved three ways in one test: an own-seat
  Digimon effect lands, an opponent Digimon effect does not, an opponent Option effect does.
- **C7 waives the cost, not the colour requirement.** `optionUseCandidates`
  (`apps/api/src/engine/effects/interpreter/actions/borrowed.ts`) keeps enforcing
  `optionColorRequirementMet` unless the action sets `waiveColorRequirement`, which this clause does
  not print. On this Black/White host a RED `[Huckmon]` Option (BT6-093) therefore needs a red
  permanent in play, while the white BT23-099 is reachable off the host alone. This cost me a first
  round of red test failures and is recorded as a dedicated test rather than papered over; every
  other positive fixture seats a red BT1-013 ally as the colour enabler (which doubles as the
  non-white suspend control).
- **C7's `sourceFilter` deliberately omits `isSelfRef`.** Per REVIEW-NOTES, the `whenSuspended`
  branch's `whenSuspendedSelfGate` ignores the rest of `sourceFilter`, so a self-ref watcher would
  silently drop the `colors: ["White"]` narrowing. "Any of your white Digimon" is board-wide anyway.
- **C5 names the shared token registry entry.** `TOKEN-Hinukamuy-Token`
  (`packages/shared/src/cards/tokens.ts`) already carries exactly the printed stat line
  (White, 6000 DP, no level, `＜Alliance＞ ＜Reboot＞ ＜Blocker＞`), so the action passes the registry
  name rather than minting a divergent inline `TokenSpec`. No "if you don't have" gate is printed,
  unlike EX13-014, so a second token is legal — proved.
- `match: "text"` carries **no** `printedTextOnly`: the C7 pool is cards in the hand and in a
  digivolution stack, not live permanents, so the live-stack over-read seam REVIEW-NOTES documents
  cannot arise. The C2 materials are likewise trash cards.

## Remaining ambiguity

- C1's widening beyond the catalog EvoCost (a non-black Lv.5 carrying the token) is proved by
  ST12-08, which is red; the cost asymmetry (4 vs 5) makes the route unambiguous, so nothing here
  rests on a structural assertion alone.
- Whether declining the C7 window spends the `[Once Per Turn]` use is the unresolved question
  REVIEW-NOTES records for `CardEffect.frequency`. The decline test asserts only the unambiguous
  half (the Option stays in hand and memory is untouched); it makes no claim about the budget.
- `[Hinukamuy] Token` carries ＜Alliance＞. No test puts it into a real attack, so its alliance
  window is out of scope for this card's clauses (it belongs to the token definition, already
  shipped, and to BT23-057's audit).
