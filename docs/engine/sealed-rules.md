# Sealed rules source ledger

## Authorized profile

Accessed 2026-10-31. The authorized first release uses the current official sealed regulations, superseding the historical BT07 sheet. The immutable engine profile is `sealed-v1`; constructed remains the default for records without a profile.

The sealed override applies to digivolution requirements; it does not override other mechanics or explicit effect selection conditions.

## Product and event policies

The creator selects an eligible English/world product before creating the private series or Sealed Swiss event. Every player receives six packs from that frozen configuration. The [product catalog and audit](sealed-products.md) records the supported released products through BT26 and EX13, actual combined English releases, unavailable products, sources, coverage and estimated collation. Collation is a versioned simulation, not a guarantee of physical Bandai box distribution. Unreleased, unknown and incomplete products are rejected. Opening never generates tournament pulls. Completed browser presentation gates deck construction; the API validates submitted decks against the allocated pool. Once pools are allocated the event cannot be deleted; audited cancellation and drops preserve its records.

The default build window is thirty minutes. Entrants without an initial legal ready deck at expiry are dropped with an audit entry; fewer than two ready entrants cancels the event. No fallback deck is generated. Between matches, a two-minute preparation window starts from the persisted series resolution timestamp, or publication of a bye. Its key and deadline survive refresh, round publication and store restarts. The next first game waits for ready participants until that deadline; expiry retains each previous legal submitted deck. The default BO3 between-game window is also two minutes and consumes the existing series clock. Both windows close when a game is allocated; locked per-game snapshots cannot change.

Explicit effect filters remain authoritative, including a Hybrid effect selecting a particular color of Tamer, a destination color selected by an effect, Option use requirements, Link requirements and DigiXros materials. The color waiver is applied to the subsequent digivolution requirement rather than to those filters. Alternate digivolution badges and DNA recipes are digivolution requirements and receive the waiver while retaining their other predicates.

## Differences from the historical sheet

The current source expressly demonstrates alternate and DNA color waivers and adds level-three breeding placement. The older source's special wording about effect/Hybrid color requirements must not be used to restrict the current profile to ordinary printed digivolution costs. Explicit card-text selection restrictions still require source-aware treatment.

Sealed events require Swiss BO3; omission defaults to BO3 at the parser and persistence boundaries, while explicit BO1 is rejected.

The focused source regressions cover ordinary and alternate color waivers, both DNA levels and material count, explicit Hybrid Tamer colors, Option use colors, paid/free and revealed-card effect digivolution and breeding placement without On Play. The external Phase 0 report records exact commands, counts, browser evidence and verification limits.

Additional regression mapping: `sealedLifecycle.test.ts` covers between-match/bye preparation, next-round first-game locks, fair sweeps beyond twenty events, BO3 persistence and sanitized organizer responses; `sealedConfiguration.test.ts` covers parsing and validation; `sealedDigivolveRoutes.test.ts` covers ordinary and alternate projected choices; `sealedCandidates.test.ts` covers bot fallback legality; `sealedReplay.test.ts` records placement and cross-color evolution, extracts the room log, and compares full replay with a restored snapshot.

## Standalone private BO3

Private Sealed is available from Play independently of Sealed Swiss. It uses the same `sealed-v1` engine profile, pool validator and versioned creator-selected product simulation described above. Each of exactly two seats receives six packs once, including guest seats. The creator’s persisted configuration controls the guest allocation, presentation and every game’s preparation timing. Only prefeature states without a configuration use BT4 compatibility. All currently supported products contain twelve pulls per pack. A browser's HttpOnly SameSite Strict cookie authenticates its seat; invitation URLs contain only the join code. Clearing that credential loses ownership of the existing seat, rather than allocating a replacement pool.

The Aegis BO3 interpretation permits pool-constrained exchange between games; this is an event policy, not a new claim about the official document's wording. Initial preparation lasts thirty minutes from creation. If both legal decks are not locked by the deadline, preparation cancels. Between games, both players can lock their next decks to start early. At two minutes, each player's last legal submitted deck is used, including an unchanged previous deck for a player who did not ready again. A start request atomically freezes both snapshots. Ready retries cannot change those snapshots or an earlier game. Only authoritative room results advance the score; first to two wins completes the series and draws do not award wins.

Either seat can cancel or forfeit the series. Unplanned in-game disconnects use the ordinary room's reconnect grace and concession rules. Pools, ready revisions, deadlines, scores and locked snapshots survive process restarts; an active engine does not. A start/reconnect request finding its persisted room absent cancels the interrupted series instead of replaying a game or generating new pools. An allocated room with no players expires through the normal waiting-room timeout. Opponent pools are never listed, spectated or included in participant replays.

Completed private-game outcomes are journaled on the server before PostgreSQL delivery. While delivery is pending, another game cannot be authorized; reconciliation retries the same authoritative outcome. A result ledger prevents duplicate scoring, including after a later game has begun. The journal survives room disposal and can be replayed after process restart when its storage is retained. This recovers a completed outcome, not an active engine. If neither database nor journal storage could retain an outcome before the process was lost, the server cannot reconstruct it from a client claim.

## Opening and browser presentation

Allocation remains immutable and server-owned. The shared original booster presents those existing packs without drawing or rerolling cards. The bounded deck editor receives only the multiset of completed packs. Selecting a carousel pack, drawing its allocated cards, charging, tearing, or revealing only part of a pack does not admit that pack to deck construction. Finishing the reveal or using the original Reveal all / Skip animations controls completes it. Animated bulk opening completes each pack at its original tear transition. Opened-history inspection cannot interrupt an unfinished opening or admit another pack.

One manifest-keyed source owns both the opener and builder progress. Its session-storage record retains separate drawn and completed counts plus the exact presentation phase, cards, batch and reveal cursor. Equivalent polling responses, reopening and same-tab reload restore that record. The stored version is upgraded in place from the earlier presentation format: a summary covering every drawn pack retains its completion; an unfinished first pack stays pending; an intact initial bulk batch retains only the packs whose transitions completed. Ambiguous legacy history summaries restart presentation from the immutable allocation because the old cursor cannot prove earlier reveal completion. Missing or invalid records start with zero eligible cards. This store is browser presentation, not server authorization. It does not synchronize across devices or independent tabs; those contexts must open their existing allocation themselves. Clearing storage loses presentation progress without changing the allocated pool. If storage is unavailable, in-memory progress works and the opener displays its existing storage warning.

Owned-copy and artwork limits use only eligible pulls. The API continues to validate final decks against the complete immutable pool and exact allocated printings; browser progress grants no new ownership. A client can already read its allocated pulls from its own API response. Server-side opening attestations and cross-device progress are outside this presentation change.
