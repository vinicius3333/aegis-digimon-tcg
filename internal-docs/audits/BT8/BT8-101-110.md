## Scope and evidence method

The ten cards were reviewed in exact ascending order. For each card, I inspected the committed catalog entry, ran exactly one local knowledge-base query, checked applicable rules/rulings/errata/restrictions, read the direct TypeScript module, compared the generated effects snapshot as read-only evidence, inspected shared interpreter primitives, read focused tests, compared same-mechanism peers, checked trait/name/color boundaries, and checked a legal evolution stack where applicable. These are Options except BT8-110's effect-driven evolution step, so a conventional card evolution stack is not applicable to BT8-101 through BT8-109; BT8-110's in-effect evolution is covered in its card section.

The one-query-per-card command was run once, in range order:

```text
for card in BT8-101 BT8-102 BT8-103 BT8-104 BT8-105 BT8-106 BT8-107 BT8-108 BT8-109 BT8-110; do node tools/kb/query.mjs card "$card"; done
```

The local KB returned Q1781 for BT8-101, Q1782 for BT8-102, no entry for BT8-103, no entry for BT8-104, Q1783-Q1785 for BT8-105, Q1786-Q1787 for BT8-106, Q1788 for BT8-107, no entry for BT8-108, the BT8-109 erratum, and the BT8-110 erratum plus Q1789-Q1791. No second local query was run.

No tests, typecheck, lint, formatter, browser/UI check, or `git diff --check` was run, per the audit instruction. The five canonical score components therefore use an executed-gate value of 0/2 for every card's final component; the resulting 8/10 scores are provisional ceilings, not claims of behavioral execution.
