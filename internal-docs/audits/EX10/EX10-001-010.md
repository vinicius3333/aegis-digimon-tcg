### Type errors resolved

Only EX10-010 appears in `TYPE-ERRORS.txt` for this batch:

```
EX10-010.ts(93,11): 'while' does not exist in type 'ModifyDPAction'.
EX10-010.ts(117,11): 'while' does not exist in type 'GrantImmunityAction'.
```

`while` here was **not** dead code. `runAction.ts:192` computes the per-action gate as
`action.condition ?? ("while" in action ? action.while : undefined)`, so an untyped `while` on any
action kind is read by the shared gate. Only `AuraAction` and `RestrictAction` declare `while`, and
only those two handlers additionally read it (to mark the grant continuous); `ModifyDP` and
`GrantImmunity` take their continuous marking from `ctx.continuousPass` and from
`primitives.continuousOpt()` instead. The typed spelling of exactly the same gate is therefore
`condition`, which the same expression reads with higher priority. I renamed both fields; runtime
behavior is unchanged and the clause the field encodes ("While your opponent has a Digimon with
13000 DP or more") still runs, re-evaluated on every continuous pass as KB Q5026 requires.

I considered the canonical `Aura { effect: { kind: "modifyDP" }, while }` shape for the DP half. I
did not adopt it: `runStaticAction` hardcodes `EffectDuration.UntilEachTurnEnd` for auras, which
would change the recorded modifier duration away from `permanent`, and I cannot run the suite to
prove the sweep interaction. The `condition` rename is the change with provably identical runtime
behavior.

## 4. Per-card findings

### EX10-001 Flickmon (DigiEgg, Green, Lv.2, [Appmon]/[Flick], System)

- **Clauses.** Inherited only: "[Your Turn] [Once Per Turn] When effects trash any of this
  Digimon's link cards, gain 1 memory." Play cost -1, DP 0, no requirements, no Security text.
- **IR trace.** `YourTurn` + `isInherited` + `frequency: OncePerTurn` → `SubTrigger`
  `whenLinkTrashed` → `GainMemory 1`. `primitives.ts:2194` fires `whenLinkTrashed` with
  `subjectPermanentId = entry.hostPermanentId` for every genuine link-card trash on the board, and
  `detach.ts` documents that a replaced link does not route through it (Q5006).
- **Defect corrected.** The watcher carried **no `sourceFilter`**, so `matchingSubjectPermanentIds`
  applied no gate and the effect gained memory when *any* link card anywhere was trashed —
  including a neighbour's and the opponent's. Printed text says "this Digimon's link cards".
  - Before: `{ kind: "SubTrigger", event: "whenLinkTrashed", actions: [GainMemory 1] }`
  - After: same, plus `sourceFilter: { isSelfRef: true }` and a `raw` provenance string.
  - `trigger.ts:72` resolves `isSelfRef` against `subCtx.source.permanent()`, which for an
    inherited effect is the host permanent — the same shape EX10-030 and EX10-073 already use for
    the identical printed phrase.
- **Tests added.** "scopes the watcher to this Digimon's own link cards" (IR); "does not gain
  memory when another Digimon's link card is trashed" — a neighbour's link and an opponent's link
  are trashed with no memory change, then the host's own link still pays out. Removed an unused
  local in the pre-existing negative test.
- **Mutation check.** Drop `sourceFilter` → the new negative case fails on the neighbour's trash.
  Change `amount` → both positive assertions fail. Drop `frequency` → the second-link assertion in
  the pre-existing test fails. Change `trigger` to `AllTurns` → not currently pinned (see score).
- **Open ambiguity.** None.

### EX10-004 Cupimon (DigiEgg, Purple, Lv.2, [In-Training]/[Mini Angel])

- **Clauses.** Inherited only: "[Your Turn] [Once Per Turn] When any of your Digimon with
  [Lucemon] in their names move from the breeding area to the battle area, by trashing 1 card in
  your hand, ＜Draw 1＞ and gain 1 memory."
- **IR trace.** `YourTurn` + `OncePerTurn` → `SubTrigger` `whenMovedFromBreeding` with

  `primitives.ts:1958` fires the event with the moved permanent as subject, so Q5010 (the moving
  Digimon holding this card in its own stack) is satisfied by the subject gate.
- **Defect corrected.** `GainMemory` was gated on `condition: { kind: "ifThisEffectActed" }`. The
  printed text has no "if you do" between the draw and the memory gain; both are results of the one
  paid processing condition. `resources.ts:40` sets `lastEffectActed = drewAny`, so with an empty
  deck the draw moves zero cards and the memory would be wrongly withheld. The gate is also
  redundant on the decline path: `subTrigger.ts:1181` breaks the body loop as soon as
  `runAction` returns the `abortOnDecline` signal, which `runAction.ts:467` returns whenever the
  cost is declined or unpayable.
  - Before: `{ kind: "GainMemory", amount: 1, condition: { kind: "ifThisEffectActed", raw: "if you did" } }`
  - After: `{ kind: "GainMemory", amount: 1 }`

  rest of the sequence. I added the empty-hand negative anyway, since the behavior was unguarded:

## 6. Seam requests

1. **`while` is untyped on every action kind that is not `Aura`/`Restrict`.** The shared gate in
   `runAction.ts:192` deliberately reads `("while" in action ? action.while : undefined)` for all
   97 action kinds, but only `AuraAction` and `RestrictAction` declare the field. Any card author
   writing the printed "While …" wording on a `ModifyDP`, `GrantImmunity`, `GainKeyword`, or
   `MinDpFloor` gets code that runs and a build that fails — the mismatch that produced EX10-010's
   two type errors, and (per `TYPE-ERRORS.txt`) similar ones elsewhere in EX10.
   - Proposed diff (`packages/shared/src/effects/ir/actions/base.ts`), one field on `ActionBase`
     with the semantics the gate already implements:
     ```ts
     /**
      * Board-state gate re-evaluated on every continuous pass, for a printed "While ..." clause.
      * Read by the shared per-action gate as `action.condition ?? action.while`; `Aura` and
      * `Restrict` additionally use its presence to mark the grant continuous.
      */
     while?: Condition;
     ```
   - Failing test the change needs: a typecheck-only fixture asserting that a `ModifyDPAction`
     literal carrying `while` compiles, plus a runtime case that a `while`-gated `ModifyDP` lapses
     on the next `recomputeContinuousEffects()` once the gate stops holding. I did not make this
     change — it is in `packages/shared`, which this batch may not edit — and instead used
     `condition`, which is behaviorally identical today.

2. **`digivolutionRequirementsFor` cannot see a card module's own requirement.**
   `packages/shared/src/effects/data.ts:1099` resolves through
   `ALTERNATE_DIGIVOLUTION_OVERRIDES → GENERATED_DIGIVOLUTION_OVERRIDES → compiledEffects`
   (`effects.json`) and never consults `registeredCompiledCards`, which
   `compiledCards.ts:14` calls "the runtime source of truth" for everything else. A hand-fixed
   `digivolutionRequirement` in a module is therefore inert until `effects.json` is regenerated.
   No card in this batch is currently affected (EX10-006/007/008 did not drift on that field), but
   the asymmetry silently swallows exactly the kind of fix this audit produces.
   - Failing test the change needs: register a module whose `digivolutionRequirement` differs from
     `effects.json`, then assert `digivolutionRequirementsFor(cardId)` returns the module's value
     — i.e. an API-boundary test in `apps/api` that injects the runtime registry, since shared
     cannot import from the engine.

3. **`runContinuousPass` has no fixpoint iteration, so mutually-dependent continuous grants never
   settle.** `GameEngine.ts:2821` clears every continuous contribution and then resolves each
   continuous effect exactly once in `continuousPriority` order. A continuous grant can therefore
   never satisfy another continuous gate, which is why EX10-010's Q5013/Q5202 loop reaches
   15000/12000 instead of 15000/15000, and collapses to 12000/12000 once the seeding Digimon
   leaves. Priority ordering cannot fix a mutual cycle.
   - Proposed diff (`apps/api/src/engine/GameEngine.ts`), iterate the derive half to a fixpoint
     while keeping the single clear:
     ```ts
     private async runContinuousPass(noPromptAsk: DecisionApi): Promise<void> {
       // ... existing clearContinuous calls, unchanged ...
       const MAX_CONTINUOUS_ITERATIONS = 4; // cycles settle in 2; the cap bounds pathological IR
       let previous = "";
       for (let pass = 0; pass < MAX_CONTINUOUS_ITERATIONS; pass++) {
         if (pass > 0) { /* re-clear ONLY the derived tiers, then re-derive */ }
         await this.deriveContinuousEffects(noPromptAsk);
         const snapshot = this.continuousStateFingerprint();
         if (snapshot === previous) break;
         previous = snapshot;
       }
     }
     ```
     The real work is extracting the existing derive loop into `deriveContinuousEffects` and adding
     a cheap `continuousStateFingerprint()` over the DP/keyword/restriction ledgers. The cap plus
     the fingerprint break keeps it terminating on IR that genuinely oscillates.
   - Failing test the change needs: it already exists, as
     `EX10-010.test.ts > "Q5013/Q5202 two-facing-copies loop: the recompute pass reaches only the
     direct half"`. Flip its three ✗ expectations to the ruling values (`mine` 15000 and immune;
     both 15000 after the seeding Digimon leaves) and it becomes the regression test for the fix.
     A second, non-EX10 case should cover a deliberately oscillating pair to prove the cap.

4. **The `nameOrTrait` type contract contradicts the interpreter, and the interpreter wins
   silently.** `packages/shared/src/effects/ir/filters/cardPredicates.ts` documents the field as
   "Entries AND by default. One entry carrying `orPrevious` switches the WHOLE array to OR", while
   `matching/definition.ts:163-169` unconditionally ORs (`filter.nameOrTrait.some(...)`) and its own
   comment states "A multi-entry `nameOrTrait` array is a UNION (OR) … both paths are OR". This
   produced EX10-006's over-wide filter, and it is a silent trap: a card author writing the printed
   conjunction gets a filter that is strictly too permissive, with no type error and no runtime
   warning. It is very likely to be wrong on other cards across the corpus.
   - Proposed diff: correct the doc comment on `CardPredicates.nameOrTrait` to state the union
     semantics and to direct conjunctions at `traits` + `nameOrTrait` (or at declaring `and` on
     `Filter`, which `definitionMatches` already reads at line 88-90 but which the type does not
     expose). Declaring `and?: Filter[]` / `or?: Filter[]` / `not?: Filter` on `Filter` would make
     the already-implemented conjunction reachable without the two-field workaround.
   - Failing test the change needs: a `definitionMatches` unit case asserting that
     `{ nameOrTrait: [{tokens:["Virus"],match:"trait"}, {tokens:["Greymon"],match:"name"}] }`
     matches a Vaccine Greymon — pinning the union as intentional — plus a corpus sweep for
     multi-entry `nameOrTrait` arrays whose printed clause is a conjunction. I did not run that
     sweep; it is outside this batch's ten cards.

5. **No seam is needed for anything else in this batch.** Every other clause on EX10-001 – EX10-010
   is expressible with existing IR and interpreter primitives.
