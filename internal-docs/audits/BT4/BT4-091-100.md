# BT4-091–BT4-100 implementation audit

> Archival notice (2026-09-02): the static-only scores and deferred-gate status below are historical. The completed 115-card ledger and executed gates are authoritative in `docs/audits/BT4-STATIC-AUDIT.md`.

Date: 2026-08-27
Scope: BT4-091 through BT4-100, in exact ascending order
Mode: static-only audit; execution gates intentionally deferred

## Executive summary

All ten assigned cards have direct TypeScript compiled IR with `coverage: "full"`,
empty residuals, and one executable registration path: `registerIrCard(cardId,
compiled)`. The direct modules match the catalog and the local rules knowledge base
after tracing their actions through the shared interpreter, with one proven direct
correction: BT4-096 used an unsupported `RevealAdd.rest` value that sent its cards to
the bottom of the deck instead of the printed top-of-deck destination; its focused
order proof now distinguishes the top from the bottom with an unrevealed sentinel.

The BT4-094 focused proof also had a fixture mismatch: it requested a `byRule`
deletion while giving the target 3000 DP, so it did not model deletion by dropping to
zero DP. That fixture now uses `dp: 0`; no shared-engine change was needed. The
generated `packages/shared/src/effects/effects.json` records remain stale in several
places and were not edited; direct registered modules remain authoritative.

This pass did not run tests, typecheck, lint, formatting, browser/UI validation, or
`git diff --check`, as required. Each card therefore scores 0/2 for executed gates
and is reported as 8/10 provisional; this report does not claim 10/10 or collection
completion.

### Shared interpreter trace

The shared paths were inspected without execution:

- `apps/api/src/engine/effects/interpreter/actions/reveal.ts:511-550` handles the
  rest destination. It orders multiple returned cards and places them at the top
  only when `action.rest === "deckTop"`; any unsupported value falls through to
  deck bottom. `RevealAdd` records `lastRevealedCards` before disposing the rest,
  and `conditions.ts:133-137` evaluates
  `triggerAllRevealedMatchFilter` against those cards. This proved BT4-096's
  unsupported `deckTopAnyOrder` value was a direct behavior gap. Changing it to
  `deckTop` preserves the any-order decision and makes the returned cards topmost.
- `apps/api/src/engine/effects/interpreter/actions/statics.ts:17-81` evaluates
  Aura conditions continuously. This supports BT4-094's color-independent
  security-count aura and BT4-095's temporary cost modifier.
- `apps/api/src/engine/effects/interpreter/actions/resources.ts:243-445` resolves
  `CostModifier` against the target Digimon and `into` definition;
  `matching/definition.ts:227-230` supports `effectTextContains`, and
  `GameEngine.ts:1495-1512` applies the active evolution-cost adjustment. This
  supports BT4-095's any-Digi-Burst interpretation from Q1247.
- `actions/subTrigger.ts:886-894` maps `deleteCause: "dpReachedZero"` to a
  by-rule removal gate, while the deletion primitive derives the DP-zero fact from
  the target's actual current DP. The corrected BT4-094 fixture now represents that
  cause rather than a 3000-DP arbitrary by-rule deletion.
- `actions/subTrigger.ts:216-229` resolves `whenSecurityRemoved` relative to the
  watcher's owner. The security primitive/event paths publish removals from the
  relevant stack, and Security effects resolve before the Security card leaves the
  stack (`security/securityCheck.ts:250-289`), supporting Kari's own-stack scope
  and Q1253's same-card timing rule.
- The combat controller publishes `whenBlocked` only after an actual block
  (`apps/api/src/engine/combat/controller.ts:1065-1067`), so BT4-098's nested
  trigger is narrower than an attack targeting a Digimon, as required by Q1254.
- `actions/play.ts:148-258` provides the no-cost play path used by all seven Tamer
  Security effects in this range; `actions/board.ts:50-109` implements the suspend
  and unsuspend state transitions used by Marcus, Thomas, Tai, Yoshino, and Kari.
- `ActivateMain` in the Security records for BT4-099 and BT4-100 re-enters the
  direct compiled card record through the registration precedence above, so the
  Security tests exercise the same Main IR rather than an older snapshot.

No shared engine or shared IR seam was modified in this range.
