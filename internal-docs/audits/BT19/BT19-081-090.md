## Scope and authority

This report covers exactly BT19-081 through BT19-090 in strict ascending card-ID order. The catalog authority is the immutable catalog blob `efbecc002fb9000789123e2f91f201466e1e5b0a`. Each card was compared with the local rules knowledge base, direct TypeScript module, read-only generated IR, shared interpreter/runtime seams, peer implementations, legal stacks, and behavior-driving test source.

All ten direct modules have full compiled coverage with empty residual coverage and register executable behavior exclusively through `registerIrCard(cardId, compiled)`. No audited card has a second `registerCard` registration. The generated `packages/shared/src/effects/effects.json` snapshot and `BT19-STATIC-AUDIT.md` were not modified.

This is a static/source-proof audit. `Executed delivery gates` is fixed at `0/2` for every card because this dispatch explicitly prohibited all tests, typecheck, lint, formatter, browser/UI, focused/mechanism/collection gates, and `git diff --check`. Structural assertions and manually injected timing/events are supplemental only and do not earn behavioral `2/2`. This report makes no collection-completion claim and does not mark the Orca worktree completed.

## Fixed scoring model

Each card receives exactly five two-point dimensions:

1. Catalog/rules — catalog fidelity and applicable KB rulings.
2. IR trace — direct compiled trigger/action/requirement trace and exclusive registration, with generated IR recorded as read-only comparison evidence.
3. Behavioral proof — observable state changes from behavior-driving tests; structural assertions and injected timing alone do not earn `2/2`.
4. Peer and stack proof — useful peer/runtime comparison and legal stack/target coverage.
5. Executed delivery gates — fixed at `0/2` by the task boundary.

The range subtotal is `67/100`, with an average provisional score of `6.7/10`. Scores are capped provisionally at `8/10` by the fixed gate boundary.

## BT19-086 runtime contract audit

The high-risk shared-cost question was resolved against existing contracts before delivery:

- `canPayCost` documents a conservative feasibility precheck. Its compound branch requires every nested cost to be payable; `payCost` calls that compound preflight before entering the nested payment loop. For BT19-086, the existing `suspend` preflight counts unsuspended candidates and the existing `deleteOwn` preflight counts matching battle-area permanents, so fewer than four Device Options fails before suspension in the ordinary stable-state case.
- `resolvePermanentTargets` enforces fixed counts: with `count: 4`, it returns exactly four selected permanent IDs when more than four candidates exist and cannot satisfy a non-up-to target with fewer. `deleteOwn` then invokes `ctx.fx.deletePermanent` and requires every selected permanent to be deleted before reporting the cost paid.
- `deletePermanent` is the normal permanent leave pipeline. It evaluates deletion/leave prevention and subtriggers before batched movement; `GameStateAccess.deletePermanent(s)Batched` moves the whole permanent stack to the relevant card owners' trash. The direct target is restricted to own battle-area Device Options, so selected permanent cards use that owner-aware route.
- Hand/trash behavior is unchanged. The final atomic commit changes only `BT19-086.ts` and `BT19-086.test.ts`; `apps/api/src/engine/effects/interpreter/costs.ts` has no final diff. Existing hand and trash branches still use their prior loose-instance candidates and `ctx.fx.trash` paths.
- The preflight contract is not transactional rollback: if a dynamic leave-prevention/replacement decision changes after preflight, a later nested payment can fail after an earlier nested component has paid. This existing limitation is disclosed rather than claimed as full behavioral proof. The broad shared `trash`-in-battle-area implementation was removed, so peer cards receive no new shared behavior from this dispatch.
