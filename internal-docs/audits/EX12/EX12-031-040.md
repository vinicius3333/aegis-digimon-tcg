### Cross-batch defect patterns (follow-up)

**Pattern 1 — Decode host scoping. Confirmed and applied.** CR 16-36-1 reads "you may play 1 specified Digimon card from **that Digimon's** digivolution cards". `targeting/loose.ts:270-300` only narrows a `digivolutionCards` candidate to the resolving permanent when the target carries `source: "thisDigimon"` (line 253, `fromThisDigimon`) or a `hostFilter`; otherwise the pool is every stack in the seats the filter scopes, so a Decode host with an empty or unhelpful stack could play a card out from under a NEIGHBOUR Digimon. Four of my cards had the unscoped shape — EX12-031 (main and inherited replacements, 2 sites), EX12-032 (inherited), EX12-035, EX12-036 — and all now carry `hostFilter: { isSelfRef: true }`, matching batch B's EX12-014. For an inherited Decode, `ctx.source.permanent()` is the host Digimon carrying the inherited effect, so `isSelfRef` is the correct anchor there too. EX12-034's `PlayWithoutCost` is NOT affected: it already scopes with `target.source: "thisDigimon"`, the other mechanism the same code path honours. Each of the four cards gained a "never from a neighbor's stack" test that would have failed before the fix: the Decode host is deleted `byEffect` with an empty stack while a neighbour holds a card matching that card's own Decode filter, and the test asserts the foreign card is still under the neighbour and never reached the battle area.

**Pattern 2 — Digi-Egg undercounting. Checked; does not apply to this batch, and I disagree with the premise for both named cards.**

- EX12-033's scaling is `{ per: 1, usePaidCount: true, filter: { controllerDefault: "mine" }, unit: "cards" }`. It scales on the cards the TRASH COST actually paid from hand ("for each card this effect trashed"), not on digivolution cards at all. There is no digivolution-card scaling on this card and no `kind` filter to drop.
- EX12-037's `chooseScaling` is `{ per: 5, filter: {}, unit: "digivolutionCards" }` — the filter is already empty, and `scaling.ts:266` applies `definitionMatches(filter, ...)` per stack card, which an empty filter satisfies for every card including catalog kind `DigiEgg`. The printed text says "for every 5 of this Digimon's digivolution cards" with no kind restriction, so counting the egg is correct and is what the code already does.

No module change was warranted. I did add the missing proof to EX12-037: a stack of one Digi-Egg (BT1-001 Yokomon) plus four Digimon reaches the five-source step and activates exactly one bullet. Had the batch-B defect existed here it would have counted 4 and activated nothing, so this test discriminates the pattern precisely.

### S-2 — no engine change requested

Every primitive these ten cards use already carries the semantics the printed text and rulings need, including the two the ledger might have been expected to miss: `modal.ts` implements the EX12-037 "for every 5" repeat/ordering rules by name, and `staticModifier`'s on-field base guard is what makes EX12-039/-040 correctly silent in the breeding area. No engine diff is proposed.

The Decode host-scoping defect is a card-IR omission, not an engine gap — `targeting/loose.ts` already honours both `hostFilter` and `source: "thisDigimon"`. Worth noting for the wider sweep though: the interpreter defaults to the UNSCOPED pool, so every Decode card that states neither is silently board-wide. If the set has more Decode cards than the four here and EX12-014, they are all suspect. A cheaper permanent guard would be for the compiler to emit `hostFilter` whenever it emits `playedByDecode: true`, since CR 16-36-1 admits no other reading — but that is a compiler change outside my surface.
