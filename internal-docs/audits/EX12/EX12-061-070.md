## 3. Registration and runtime findings

- Every module keeps exactly one `registerIrCard("EX12-0XX", compiled)` and no `registerCard`.
- Persisted-IR drift: **none** in this batch. I re-compared all ten modules against their
  `effects.json` records field by field; each record is identical to the module, including the
  hand-fixed additions on EX12-063 (`baseColors`), EX12-065 (`playCostLte`), EX12-069
  (`sameLevelAsAttacker`, `reduceCostBy`) and EX12-070. No record carries a hint the module lost
  and no module carries a hint the record lost. There is therefore no "which side won" verdict to
  give for any card in the batch.
- `coverage: "full"` and `residual: []` are honest for all ten: every printed clause reaches a
  concrete interpreter path (see the per-card traces).

### Interpreter facts established for this batch

- `builderForTrigger` (`effect.ts:293-301`) routes `isSecurity` combined with
  `YourTurn`/`OpponentsTurn`/`AllTurns` to the `securityStatic` builder and gives it
  `EffectTiming.None`, so EX12-069's `[Security][Your Turn]` clause is a resident watcher on the
  face-up security card, not a one-shot security-check skill. Only `isSecurity` + `Security`
  becomes `SecuritySkill`. The IR shape used by EX12-069 is the documented one.
- `withIntrinsicDelayGate` (`effect.ts:372`) stamps `delayArmedIntrinsic` on every top-level
  `SubTrigger` of a ＜Delay＞-keyworded continuous effect, and `runSubTrigger`
  (`actions/subTrigger.ts:1097-1128`) then enforces comprehensive rules 16-17: no activation on
  the turn the Option entered play, an explicit optional ask, and trashing the Option as the
  activation cost. EX12-070 therefore does not need `requiresDelayArmed`, and matches BT19-099.
- `runEffect` (`effect.ts:545-560`) converts an actionless effect that only carries `keywords`
  into a self-targeted `GainKeyword`, permanent for a `Static` trigger. EX12-065's
  `Static`/`Fortitude` node is the supported encoding.
- `sameLevelAsAttacker` (`actions/play.ts:456-468`) resolves the attacker at *activation* time
  from the live permanent and yields an empty candidate set when no attack is open. That is
  exactly EX12-069 Q6882.
- `SecurityManipulation` `placeAsSecurity` with no `source` (`actions/security.ts:354-362`) is the
  self form and relocates `ctx.source.instanceId`; `toHand` with `toTop: false`
  (`actions/security.ts:255`) reads the bottom card. Both EX12-069 `[Main]` actions are correct,
  and neither aborts on an empty stack (Q6876).
- Comprehensive rules 16-42: ＜Use Req.＞ only lets a player *ignore the colour requirement* when
  the named cards are on the field. `WaiveColorRequirement` gated by a `youHave` condition is the
  faithful encoding, and matches EX12-074's peer shape. It is **not** a play gate.

Clauses: Purple/Black, Lv.5 Ultimate, Virus, 7/7000, [Cyborg]/[ME]; `[Digivolve] Lv.4

**Type errors resolved (2).** The module declared

```ts
const deleteOrDeDigivolve = [ { kind: "Delete", ... }, { kind: "DeDigivolve", ... } ];
```

without a type annotation. TypeScript widened every `kind` to `string`, so the array was not an
`Action[]`, and both use sites (`OnPlay` and `WhenDigivolving`) failed to satisfy
`CardEffect.actions` — one error each. Fixed by annotating `const deleteOrDeDigivolve: Action[]`
and importing `Action` from `@aegis/shared`, the same shape EX12-052 already uses for a shared
action list. What the errors meant semantically: the two windows were never being checked against
the IR contract at all, so nothing had verified that `ifThisEffectDidNotDelete` and the
`DeDigivolve.amount` shape were real nodes. With the annotation in place I confirmed against
`predicates/conditions.ts:69` and `actions/digivolve.ts:16-31` that both are. No IR values
changed, so the module still matches `effects.json` byte for byte in canonical form.

Defects corrected: only the typing defect above; the semantics were already right. In particular
the `Delete` action carries no `optional`, which is what Q6862 requires, and
`ifThisEffectDidNotDelete` is documented in the IR as counting an immune or prevented target as
not deleted, which is Q6863.

Tests added:

1. "Q6864 fires the All Turns watcher for its own play and reactivates When Digivolving" — plays
   Megadramon from hand with one opposing level-3 Digimon and one level-6 stack. `[On Play]`

2. "Q6862 must delete an available level 4 or lower Digimon instead of taking the De-Digivolve

   is deleted and the stack is left at two cards, i.e. the delete cannot be skipped to reach the
   fallback.

3. "Q6863 falls through to De-Digivolve when the chosen level 4 target cannot be deleted" — makes
   the only level-4-or-lower opposing Digimon unaffected by Digimon effects through the continuous
   ledger (`addRestriction(..., "beAffected", EffectDuration.Permanent, { fromSourceKind:
   ["Digimon"] })`, the EX12-016 Q6740 pattern), then fires `[When Digivolving]` and asserts the
   immune Digimon survives *and* the level-6 stack is still peeled. Verified meaningful by
   mutation: deleting the `addRestriction` call makes the test fail on
   `expect(battleArea).toHaveLength(2)`.

Mutation check: add `optional: true` to the `Delete` and test 2 fails (the stack would be peeled).
Change the watcher `sourceFilter` traits so Megadramon no longer matches itself and test 1 fails.

## 6. Seam requests

No card in this batch needs an engine change to be *correct as printed*: every printed clause
reaches an existing interpreter path, and the one code change made (EX12-064's `Action[]`
annotation) is inside the card module.

Two of the three gaps from the first pass are now closed with existing testkit features
(`ledgers.continuous.addRestriction` for deletion immunity, `autoOrderTriggers: false` plus an
`orderTriggers` response for trigger ordering). The two that remain are engine seams, not testkit
gaps:

1. **＜Fortitude＞ is not orderable against the deletion window (EX12-065, KB Q6866).**
   `apps/api/src/engine/effects/primitives.ts:3308` runs the ＜Fortitude＞ replay loop after every
   deletion timing has fired, so ＜Fortitude＞ never joins the `orderTriggers` pool. The ruling
   lets the controller activate ＜Fortitude＞ first and thereby strand the card's other pending
   on-deletion effects. Proposed shape: enrol each `fortitudeReplays` entry as a pending trigger
   in the same simultaneous-trigger queue as the deletion timings, keyed to its instance, and let
   the existing ordering decision sequence it; when the replay resolves first, the instance leaves
   the trash and the remaining pending effects on that instance are dropped by the existing
   "still relevant" guard. The failing test it needs: delete EX12-065 with EX12-063 underneath and
   a legal Puppet/TB card in trash, answer the ordering decision with the ＜Fortitude＞ key, and
   assert that neither the `[On Deletion]` return nor the inherited play resolves. Today no
   `orderTriggers` option for ＜Fortitude＞ is offered at all, so the test cannot even be written.
   Impact: strictly generous to the ＜Fortitude＞ controller, and it affects every ＜Fortitude＞
   card rather than this one.

2. **No primitive can remove a trait from a permanent (EX12-069, KB Q6881).**
   `effectiveTraits` (`apps/api/src/engine/effects/continuous.ts:1660`) is printed ∪ granted with
   no subtraction; `addNameTraitGrant` and `grantedTraits` are additive only;
   `addOriginalCardInfoOverride` covers `name` and `colors` but not `types`; and no
   `RestrictionKind` (`packages/shared/src/effects/ir/actions/restrictions.ts:10-35`) touches
   traits. Proposed shape: a `nameTraitRemovals` list on the continuous ledger, mirroring
   `nameTraitGrants`, subtracted inside `effectiveTraits` after the grant union. The failing test
   it needs: attack with a level-4 [VB] Digimon so this card's face-up security watcher arms,
   remove the [VB] trait before the watcher activates, and assert the watcher still fires and
   still reads the attacker's level. This is not blocking any card in this batch — no EX12 card
   removes a trait — so it is a completeness request, filed so the next auditor does not re-derive
   it.
