### Type error resolved

`EX11-070.ts:34` — `Filter` is not assignable.

hypothesis (that `textContains` is an unread, dead field making the filter
match too broadly) is **wrong on both halves**:

- `textContains` **is** read. `apps/api/src/engine/effects/interpreter/matching/definition.ts:216`
  implements it as the "in its text" union (name ∪ traits ∪ forms ∪ attributes ∪ effect text ∪
  inherited text), string or OR-matched array, and it is declared at
  `packages/shared/src/effects/ir/filters/compilerAliases.ts:68`, which `Filter` extends. It is the
  right encoding for Q5942 and is used the same way by BT16-072/073, BT20-044 and EX10-013/015.
- The real cause was ordinary literal widening: `const maquinamonText = { controller: "mine",
  kind: ["Digimon"], … }` with no annotation infers `controller: string` and `kind: string[]`,
  neither assignable to `Controller` / `("Digimon"|"Tamer"|"Option"|"DigiEgg")[]`.

Fix: annotate the two module-level consts (`const self: Target`, `const maquinamonText: Filter`)
and import `Filter`/`Target` from `@aegis/shared`. No cast, no `any`, no semantic change. The
alternative encoding (`nameOrTrait` with `match: "text"`) is equivalent — `matchNameOrTrait`'s
`"text"` branch is the same union — and the module already uses that spelling inside the two
`selfTopHasText` conditions; I left both spellings as they were rather than churn a working field.
