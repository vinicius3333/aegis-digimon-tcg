# BT14 static card-by-card re-audit: BT14-001 through BT14-010

## Audit frame

This report independently re-audits exactly BT14-001 through BT14-010 in ascending card-ID order. The immutable catalog source was Git blob `efbecc002fb9000789123e2f91f201466e1e5b0a`; the local rules/errata/QA knowledge base was queried for every card. Historical `internal-docs/audits/BT14.md` was treated as prior evidence only and was not used as a substitute for recalculation.

The direct card modules, current interpreter and primitives, colocated source tests, realistic peer/evolution stacks, and registration paths were inspected. All ten modules currently register executable behavior only through `registerIrCard(cardId, compiled)`. No generated snapshot, collection ledger, or protected `packages/shared/src/effects/effects.json` file was changed.

Per the dispatch constraints, no tests, typecheck, lint, formatter, browser/UI check, collection/mechanism gate, or `git diff --check` was executed. Therefore executed gates are fixed at 0/2 and every score below is provisional, with a maximum of 8/10. “Behavioral proof” means the source tests contain behavior-driving assertions and natural originating-event paths; it does not claim those tests were run.

### Shared rules and interpreter trace used throughout

- The KB’s comprehensive rules sections `3-4-7-3` through `3-4-7-7` establish that breeding cards are not normally affected or chosen and that effects do not trigger there unless a breeding-area exception is explicit. Sections `7-1-1` through `7-1-3` cover playing cards and normal hand-to-battle-area play; `8-1-1` through `8-1-3` cover digivolution requirements, orientation, and payment. Sections `15-5` through `15-8` cover trigger conditions, processing conditions, optional processing, and persistent effects. Manual sections `16-8` and `16-9` cover Draw and Jamming.
- `apps/api/src/engine/effects/interpreter/effect.ts` supplies turn-scope and frequency wrappers; `registration/module.ts` applies them to registered triggers. `subTrigger.ts` enforces controller, source-kind, turn, once-per-turn, hand-trash, and effect-suspension gates. `conditions.ts` and `matching/permanent.ts` provide live field/stack matching. `continuous.ts` and `actions/restrictions.ts` preserve restriction provenance, including `byEffectOnly`; `primitives.ts` performs play, digivolution, trash, and security event dispatch. `security/securityCheck.ts` extracts security cards, fires security-removal events, and applies Jamming only in the Security Digimon battle path.
- Source tests were inspected but intentionally not executed. Exact test names and paths are recorded per card so a later runtime audit can reproduce the evidence and fill the fixed 0/2 gate component.

## BT14-001 — Koromon

### Catalog and KB clause trace

The immutable catalog record is a red Level-2 Digi-Egg with play cost -1, 0 DP, In-Training form, Lesser trait, and no evolution cost. Its inherited clause is `[Your Turn][Once Per Turn] When a card is removed from your opponent's security stack, ＜Draw 1＞.` The KB has no BT14-001-specific erratum, ruling, or banlist entry.

The clause requires the turn scope, a once-per-turn limit, the opponent’s security stack as the event source, and one draw for this player. It does not trigger when this player’s own security is removed, and the host must be a legal battle-area Digimon rather than a breeding-area card after the normal breeding restriction is applied.

### IR, behavior, and peer/stack evidence

`apps/api/src/cards/BT14/BT14-001.ts` compiles the inherited effect as a `YourTurn` `SubTrigger` for `whenSecurityRemoved`, with `sourceFilter.controller: opponent`, Draw-one for the host controller, and `OncePerTurn`; coverage is full with no residual gap. Registration is exclusively `registerIrCard("BT14-001", compiled)`.

`BT14-001.test.ts` contains a direction/once-per-turn source assertion (own-security removal does not draw; the first opponent-security removal draws; a second does not) and a natural production path: Koromon evolves to BT14-007, moves from breeding, attacks publicly, removes an opponent security card, and asserts the draw. This exercises the actual security extraction/event path rather than only injecting an event.

Peer and stack checks include the inverse security-removal watcher pattern in BT13-003 and the legal Koromon-to-Agumon stack used by the test. The shared trace is security extraction → `whenSecurityRemoved` payload → controller/source gate → turn/frequency wrapper → Draw.

### Corrections, limitations, and score

No implementation correction was required. The source proof is adequate for positive direction, negative direction, once-per-turn, and a legal moved-out-of-breeding host.
