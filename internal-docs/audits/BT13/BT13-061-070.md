## Scope and method

This audit covers ten cards in strict ascending catalog order. The catalog records were read from the immutable blob named above, rather than from a regenerated snapshot. Each card was queried against the local rules/QA knowledge base, then traced from its direct TypeScript module through the compiled intermediate representation (IR), shared interpreter primitives, generated effects snapshot, colocated behavioral source, relevant peer cards, and realistic stack scenarios.

The worker first fetched `origin/audit-bt-card-by-card` and merged it with the existing branch using the regular non-rebasing merge commit `1b30c1521` (`Merge audit-bt-card-by-card updates`). Card behavior is registered only with `registerIrCard(cardId, compiled)`; every module in this range has one such registration and no `registerCard` path. `packages/shared/src/effects/effects.json` and `BT13-STATIC-AUDIT.md` were read as evidence only and were not edited.

Source cases were added where a structural assertion did not by itself prove the relevant clause. These cases are deliberately not executed in this audit because the requested verification scope forbids tests and all other gates. Accordingly, the executed-gates component is fixed at 0/2 for every card; a source case is credited for behavioral proof only when it sets up and asserts the actual state transition or a meaningful positive/negative branch.

## Shared rules and interpreter trace

The local comprehensive rules at `data/kb/rules/comprehensive.md:216-225` distinguish a bracketed name reference from the phrase “in its name”: §2-3-1-2 treats a bracket-only name as exact, while §2-3-1-3 treats “in its name” as substring matching. The matcher implementation at `apps/api/src/engine/effects/interpreter/matching/definition.ts:273-339` implements this distinction; in particular, `match: "nameExact"` compares the normalized name token for equality, while `match: "name"` accepts the corresponding name substring. This is why BT13-062’s inherited `[Chuumon]` target is exact while its Sukamon/Etemon conditions and targets are substring-based.

The reveal process and selection/ordering seam is in `apps/api/src/engine/effects/interpreter/actions/reveal.ts:79-93,108-188,717-813`, with §15-15-3 at `comprehensive.md:2550-2665` covering reveal processing and bottom ordering. Play-without-cost source, zone, level, and optional-cost handling is in `actions/play.ts:72-100,104-330,359`. Replacement and optional-payment handling is in `actions/replacement.ts:30-70,343-368,516+`; the local rules’ immediate-type restriction at §15-8-5-5 prevents a replacement from retriggering itself before resolution, matching KB Q2308 and Q2310.

Trigger timing is covered by `comprehensive.md:2705-2740` (§15-16) for On Play, On Deletion, and When Attacking. Blocker, Jamming, Reboot, and De-Digivolve are traced through §16-5, §16-9, §16-11, and §16-12 (`comprehensive.md:2818-2948`) and the shared action seams. De-Digivolve’s level-3 floor is represented directly by `stopAtLevel: 3`; the interpreter primitive at `apps/api/src/engine/effects/interpreter/primitives.ts:1461-1493` preserves a level 3 or lower card rather than trashing it.

The `selfHasTrait` condition used by BT13-063 and BT13-066 is implemented at `conditions.ts:438-448` and reads the live top-card trait union, with permanent trait matching in `matching/permanent.ts:19-60`. The opponent-turn condition used by deletion effects is in `conditions.ts:561+`. Registration flows through `apps/api/src/engine/effects/interpreter/registration/module.ts:323-341`; all ten direct modules use this shared IR registration path only.
