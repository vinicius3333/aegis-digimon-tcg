# BT1-021 through BT1-030 Card Implementation Audit

Archival notice: final executed evidence and 10/10 scores are recorded in `docs/audits/BT1-STATIC-AUDIT.md`.

Audit date: 2026-08-27

This range was audited in ascending card-ID order against the committed catalog,
local rules knowledge base, direct card modules, compiled IR, shared engine
primitives, colocated tests, nearby peers, and available evolution-stack
fixtures. All ten modules register exactly one executable implementation through
`registerIrCard(cardId, compiled)`; no duplicate `registerCard` registration was
added or retained.

The user explicitly deferred execution. Therefore no focused tests, mechanism
tests, collection tests, typecheck, lint, format, or `git diff --check` were run,
and every score below is provisional. No card is claimed as 10/10.

## Per-card findings

### BT1-021 MetalGreymon — provisional 8/10

- Catalog: Red Lv.5, 7000 DP, play cost 6, Red Lv.4 evolution cost 3,
  `Cyborg` trait. Printed clause: `[When Attacking] Gain 3 memory. At end of
  turn, lose 3 memory.`
- KB: `node tools/kb/query.mjs card BT1-021` returned Q882 (the delayed loss
  still happens if the attacker is deleted), Q883 (passing after the gain still
  applies the additional loss), and Q1080/Q1087/Q1097 (memory-gain effects can
  be restricted while specified memory loss remains valid).
- Implementation: `apps/api/src/cards/BT1/BT1-021.ts` maps the attack trigger
  to `GainMemory +3` followed by `GainMemory -3, at: "endOfTurn"`, with
  `coverage: "full"` and `residual: []`, and registers only through
  `registerIrCard`. `apps/api/src/engine/effects/interpreter/actions/resources.ts`
  installs the delayed loss anchorlessly, matching Q882/Q883.
- Proof: `apps/api/src/cards/BT1/BT1-021.test.ts` covers immediate gain, delayed
  loss, deletion before end of turn, pass-at-3 memory behavior, and the added
  legal Red Lv.4 evolution-stack attack/delay case. Peer comparison covered the
  identical delayed-memory records in `apps/api/src/cards/BT1/BT1-040.ts`,
  `BT1-058.ts`, and `BT1-075.ts`, plus the contrasting memory-loss
  `BT1-114.ts`; `apps/api/src/cards/BT1/BT1-017.test.ts` also evolves into
  BT1-021.
- Status: every printed clause has an IR mapping and observable fixture. The
  focused/mechanism/collection gates remain unexecuted, so the score is
  provisional.

### BT1-022 Garudamon — provisional 8/10

- Catalog: Red Lv.5, 7000 DP, play cost 7, Red Lv.4 evolution cost 3,
  `Birdkin` trait. Printed clauses: `Piercing`; inherited `[Your Turn] When
  this Digimon is blocked, trigger Draw 1`.
- KB: Q884 confirms the inherited effect triggers only when an attack target is
  changed to a blocking Digimon, not when the host directly attacks an opposing
  Digimon.
- Implementation: `apps/api/src/cards/BT1/BT1-022.ts` encodes a static Piercing
  keyword and an inherited `WhenBlocked` effect with an `isYourTurn` gate and
  one mine-side Draw. `apps/api/src/engine/effects/builders.ts` binds
  `whenBlocked` to the actual attacker's permanent; `board.ts`/`resources.ts`
  provide the keyword and draw semantics; `combat/controller.ts` performs the
  block transition and Piercing sequence.
- Proof: `apps/api/src/cards/BT1/BT1-022.test.ts` covers standalone Piercing,
  blocked battle plus security check, inherited draw on a
  `BT1-023`/`BT1-022` stack, no draw on direct Digimon attack, and no draw from
  an opponent-turn block drive. Peer checks included `BT2-015.ts`, `ST1-08.ts`,
  `BT11-013.ts`, and Piercing peer `BT1-026.ts`; the mixed stack is the
  realistic evolution-source case.
- Status: both card-level and inherited clauses have positive and negative
  proof. Gates are deferred; no 10/10 claim is made.

## Ambiguities and limitations

- The local KB has no card-specific Q&A entries for BT1-024, BT1-026, BT1-027,
  BT1-028, or BT1-029. Their behavior is unambiguous from the committed catalog
  and the cited general rules, but the absence of a card-specific ruling is
  recorded rather than inferred as additional behavior.
- The catalog retains the BT1-era label `Security Attack`; the current local
  comprehensive rules call the same keyword `Security A.`. The implementation's
  internal `SecurityAttack` keyword is the intentional compatibility spelling,
  while the printed BT1 text and tests preserve the catalog meaning.
- BT1-022's inherited text says “trigger Draw 1”; local rules define `<Draw 1>`
  as mandatory once the block trigger occurs. No optional refusal is modeled for
  that clause because neither the catalog nor Q884 marks it optional.
- No relevant card-play UI flow is exposed by this server-focused worktree, so
  evolution-stack evidence uses the observable engine testkit. A browser-based
  run remains out of scope unless the audit provides an exposed client
  flow.
- Execution is intentionally deferred: focused behavior, range/mechanism,
  collection, typecheck, lint, format, and diff validation all remain pending.

## BT1 lane-A static closeout (BT1-021–030)

The independent lane-A pass rechecked each committed catalog record, one local
card-KB query per card (10 queries total), direct IR, focused test, peers, and
the combat/resource primitives in ascending order. Q882–Q884 and Q886–Q888
were reconciled with the current modules; no new semantic gap was found. The
ten range production modules now have no @ts-nocheck, no unsafe cast, no
RawUnparsed, exactly one matching registerIrCard, and empty residuals. Direct
imports were added to BT1-024.test.ts, BT1-027.test.ts, and BT1-028.test.ts;
the other focused tests already loaded their subject modules. Execution gates
remain and deferred.
