# Game feel plan — match screen animations and feedback (2026-08-24)

Goal: bring the Aegis match screen to the level of the reference client for
moment-to-moment feedback: every state change the server broadcasts gets a
visible, sequenced, skippable piece of motion or UI, and every decision the
player must make gets a clear, styled prompt.

## Sources of truth

- Reference video: `~/Desktop/Gravação de Tela 2026-08-24 às 21.39.34.mov`
  (5:40, full bot match: mulligan → breeding → plays → effects → security
  attacks both ways → DigiXros → game end).
- `docs/battle-animation-spec.md` — reverse-engineered the reference client timings
  (DOTween/`.anim` durations, easing table, per-sequence "What the web port
  should do"). Trust its timings; its `game.css` line refs are stale;
  the implemented classes are `battle-*`.
- `apps/web/src/design/DESIGN.md` — design contract. Motion rules apply:
  quiet surfaces, motion serves the current action, `prefers-reduced-motion`
  must degrade every sequence to instant state changes.
- Screenshots collected in the planning session (mulligan, hatch, played-card
  showcase, tooltips, side panels, selection flows, security clash, evolution
  cut-in, summoning-sickness ring, drag labels, DigiXros).

## Current state (what already exists)

Client is React 19 + plain CSS (no PixiJS — README/CONTEXT drift). All match
UI lives in `apps/web/src/game/`:

- `GameScreen.tsx` (2864 lines) — owns ~30 `useState` + timeout refs; one
  `useEffect([events])` (~lines 490–590) diffs new `ServerEvent`s and fans out
  to sounds, info panels, lunge, security clash, banners. `cueBaselineRef`
  suppresses replayed history on reconnect.
- `overlays.tsx` (3022 lines) — `MulliganOverlay`, `DecisionOverlay` (all 7
  `DecisionKind`s), combat prompts, zone viewers, `RecoveryToast`,
  `EffectClauseToast`.
- `boardPieces.tsx` — `PermanentView` (lunge prop), `MemoryGauge`, `Hand`,
  `AttackArrow`, `Pile`, `BreedingSlot`.
- `game.css` (3189 lines) — all `battle-*` keyframes: draw flight, card enter
  - sparkle, lunge, arrow, security hit, full security-clash scene
    (`securityClash.ts` timing table), marker pop/sweep, turn banner.
- `InfoPanelStack.tsx` — transient right-side info panels.
- `animations.ts` — `useEnterAnimation` only.

Gaps: no animation sequencing (fire-and-forget timeouts stomp each other), no
unified toast system, no opponent play/evolution showcase, no shield-break, no
summoning-sickness marker, no drag intent labels, no numbered multi-select, no
timed side panels, no hand-selection mode, timings scattered across four files.

## Hard constraints

1. Client owns zero rules (`docs/ARCHITECTURE.md` §4). Everything here is
   presentation of server events/decisions; never infer game state.
2. `uiCompleteness.test.ts` fails CI if a `DecisionKind`, combat prompt, or
   intent loses its handler — refactors must keep the registry satisfied.
3. Reconnect replay: any new queue must respect `cueBaselineRef` semantics —
   replayed history plays no animation, ends in the correct final state.
4. `DECISION_CHANNEL` reconciliation in `useRoom.ts`
   (`reconcileDecisionPatch`) must not be touched by animation work.
5. `prefers-reduced-motion` collapses every sequence to its end state.
6. Landscape-phone layout was tuned recently (`de56b2bc4`); verify each
   deliverable on the small landscape breakpoint.
7. Extract pure logic into testable modules (repo pattern:
   `securityClash.ts`, `infoPanels.ts`) with colocated Vitest files.

## Approved liberties (owner sign-off 2026-08-24)

- Refactors are allowed, including breaking up `GameScreen.tsx`.
- Animation libraries are allowed. Decision: adopt `motion`
  (framer-motion v12+) for orchestrated sequences — `AnimatePresence` for
  overlays/panels/showcases, `animate()` mini API inside the queue steps so
  "every wait is a real await" becomes literal (`await animate(...)`).
  Keep existing `battle-*` CSS keyframes where they already work; migrate
  only when a sequence needs interruption/skip support. No canvas engine.
- Heavy implementation phases run as Opus subagent tasks, one per PR slice,
  against this plan.

## Phase 0 — foundation (prerequisite for everything else)

### 0.1 Animation sequencer

The spec's core directive: "every wait is a real await… drive the sequence
from an async queue in `GameScreen.tsx`".

- New `game/animationQueue.ts`: a pure queue reducer + a `useAnimationQueue`
  hook. Server events map to _steps_; steps run serially (with explicit
  parallel groups), each step = `{ apply, durationMs, skippable }`.
- A global "skip/fast-forward" input (click during opponent sequences)
  advances the queue to its end state — the reference client lets you click through.
- Replayed history (reconnect) enqueues nothing; queue drains instantly when
  `document.hidden` or reduced motion.
- Extract the existing event fan-out effect from `GameScreen.tsx` into
  `game/useMatchCues.ts` that feeds the queue. `GameScreen` keeps rendering.

### 0.2 Timing module

- New `game/timings.ts`: single table of every duration, imported by TS and
  mirrored into CSS via custom properties (`--t-draw-flight` etc.) set on the
  battle root. Fold in constants from `GameScreen.tsx`, `securityClash.ts`,
  `infoPanels.ts`. Values come from `battle-animation-spec.md`.

### 0.3 Unified toast/notice system

Today: `flash` string, `RecoveryToast`, `EffectClauseToast`, plus
`design/SuccessToast.tsx` outside the match. Replace in-match instances with:

- `game/NoticeStack.tsx`: stacked framed notices (reference image #5/#21
  style: blue corner-framed panel, effect text + card art thumbnail), anchored
  per side — viewer effects bottom-left, opponent top-left; security effects
  mirror to the opposite side of the modal stack (reference #26).
- Queue-aware: notices spawn from queue steps, auto-dismiss with the
  border-countdown treatment (see 2.3), disperse faster when 3+ are stacked
  (reference #22).

## Phase 1 — decisions and selection UX

### 1.1 Mulligan overlay parity (reference #1)

Exists; polish to reference: title "Will you mulligan your hand?" + turn-order
callout ("You are SECOND" accent), large card row, three actions — Keep Hand /
Mulligan / Check Play Area (peek mode that hides the dialog while held).
Files: `overlays.tsx` (`MulliganOverlay`), `game.css`.

### 1.2 Hand-selection mode (references #15, #16)

New pattern for `selectCards` decisions whose source zone is the viewer's
hand: instead of a modal, enter _board mode_ — dim left rail showing "Select N
card(s) to trash." + `No Selection` (optional) / `End Selection` (confirm),
selectable hand cards get the cyan glow, selected cards get an accent border +
numbered badge (selection order). Extend `DecisionOverlay` with a
`presentation: 'board' | 'dialog'` selector in `boardModel.ts` (pure,
tested). Keep dialog fallback for zones not visible on board.

### 1.3 Bigger selection dialogs on desktop (reference #19)

`DecisionOverlay` desktop sizing: wider card grid, larger cards, header
subtitle "Select N card(s).", horizontal scroll with scrollbar for >6 options
(reference #110/#120 frames). Numbered order badges for `orderCards`
(reference #20, #145 frame: orange border + 1/2/3 badges, "cards with lower
numbers on top" helper line).

### 1.4 Multiple-effects trigger chooser (reference #17)

`orderTriggers` presentation: "Multiple effects are triggered. Choose which
effect to process." — each option rendered as its card with a source label
(`Field:1`, `Hand`, …) and a one-line clause summary overlaid on the card
bottom. Clause summary comes from existing `keywordDisplay.ts`/effect text
truncation (pure helper + test).

### 1.5 Optional-effect prompt (reference "Use / Not use", frame #150)

`optional` decisions render as the left-rail board-mode prompt: clause text
("Will you use …?") + amber `Use` / blue `Not use`, with the source card
highlighted on the field. Already dialog-based today; move to board mode so
the field stays visible.

### 1.6 "Opponent is selecting cards." (reference #6)

When a `DecisionRequest` goes to the opponent (detect from `effectActivated`
without a local decision, or add a lightweight server event if needed — check
first whether existing events suffice), show a floating dark pill near their
deck/hand. Remove on next event from them.

## Phase 2 — zone-change showcases and side panels

### 2.1 Center-screen played-card showcase (references #3, #28)

Per the spec: zone changes are hide → center overlay → reveal (never FLIP).
When the opponent plays/digivolves/uses an option, show the full card
center-screen (drop shadow, slight scale-in), hold ~900 ms (skippable), then
continue the queue: card appears on field with entrance burst. Viewer's own
plays skip the showcase (they dragged it) but keep the field burst.

### 2.2 Field entrance and evolution effects (references #4, #27, #29)

- Entrance: existing `battle-card-enter` + sparkle; add the color-keyed
  radial burst component from the spec ("one shared burst component,
  color-keyed" — effect-color vocabulary is in the spec) behind the card.
- Evolution on field: red/orange arc rings + scale pop on the evolved stack
  (reference #29); breeding evolution gets the highlighted center treatment
  (reference #11) with the egg spotlight ring (reference #2).
- Hatch (reference #2): dark radial vignette + white starburst behind the
  breeding slot when `hatched` fires.
- Effect notice (Phase 0.3 toast) fires alongside for On Play/When
  Digivolving clauses.

### 2.3 Timed side panels (references #7, #8, #18, #22, #23 + frames)

Generalize `InfoPanelStack` into titled card panels: `Discarded cards`,
`Cards added to hand`, `Selected Cards`, `Revealed Cards`, `Deleted cards`,
`Played Card`, `Deck Bottom Card`, `Digivolution Cards` — driven by
`cardsMoved`/`cardRevealed`/`effectResolved` events.

- Placement: opponent-origin panels top-right, viewer-origin bottom-right;
  when two coexist they stack vertically (reference #22 shows both).
- Lifetime: manual `×` close + auto-dismiss with a border that erodes
  clockwise showing remaining time (reference #7) — CSS conic-gradient border
  animation, duration from `timings.ts`, faster when 2+ panels are queued.
- Numbered badges over cards when order matters (revealed order — #23).
- Pure module `game/sidePanels.ts` (event → panel model) + tests.

### 2.4 Turn-start draw cue (reference #9)

Existing draw flight stays; add the blue starburst on the drawn card at the
hand slot for turn-start draws (distinct from effect draws which show the
notice toast instead — reference #18 shows both together, so they compose).

## Phase 3 — combat and security

### 3.1 Attack flow, both directions (references #24, #25, #26 + frames)

Queue-sequenced: attack declared → SVG arrow draws (exists) → target side
shield pulses → _shield break_: crack + shatter particles on the defender's
security pixel-shield icon and screen-edge flash on the defender's side →
security card flips and reveals center-stage (existing clash scene) → then
either battle resolution (existing) or security-effect branch: card slides to
the side opposite the panel stack (left), effect notice toast appears
(reference #26), effect resolves, then card animates to trash/field.

- Reuse `SecurityClashView`; extend `securityClash.ts` timing table with the
  break and effect-branch beats.
- Mirror fully for the viewer attacking opponent security (video 2:30–4:40):
  arrow up, break on top, reveal, opponent security counter decrements with a
  pop.

### 3.2 Summoning sickness ring (reference #13)

Permanents played this turn without Rush show the orbiting star ring
(5–6 gold stars on an elliptical orbit above the card, CSS animation).
Server truth: derive from the schema's play-turn/attack-eligibility field —
verify `Permanent` exposes it; if not, add a schema flag server-side (tiny
API change, no rules on client). Ring disappears at the owner's next turn
start. Also used on freshly played Tamers (reference #12 shows Xeno with it).

### 3.3 Suspend/unsuspend rotation

Currently instant. Animate the 90° rotation with the spec's timing; unsuspend
phase sweeps the board with slight stagger. The `UNSUSPEND` phase chip
(frame #150) already exists in the gauge area — keep in sync.

## Phase 4 — modes, drag feedback, chrome

### 4.1 Drag intent labels + area highlight (reference #12)

### 4.2 Breeding phase mode (reference #10)

states `End Turn`, `End Breeding`, `Opponent's Turn`, disabled.

### 4.3 Turn banners and callouts (frames #135, #140)

Full-width banner sweep for `Your Turn` / `Opponent's Turn` (exists as

from the notice system.

### 4.4 Memory gauge polish (reference #3 arc, frame #80)

Existing marker pop/sweep stays; add the red arc that traces from old to new

## Phase 5 — responsiveness pass (tablet and mobile)

Runs last, after all visual work has landed, and audits everything this plan
added plus the pre-existing match screen.

Breakpoint matrix (verify every flow in each):

- Mobile portrait (~390×844) and mobile landscape (~844×390) — landscape was
  freshly tuned in `de56b2bc4`; treat it as the regression baseline.
- Tablet portrait (~820×1180) and tablet landscape (~1180×820).
- Desktop (≥1280) — the reference layout.

Audit targets and fixes:

- Every overlay/dialog from Phase 1: card grids must reflow (fewer columns,
  horizontally scrollable rows with visible scrollbar/affordance on touch),
  buttons reachable by thumb, no dialog taller than the viewport.
- Side panels and notice stack (Phase 0.3/2.3): on narrow widths collapse to
  a single stacked column, cap panel width, keep the timed-border dismiss
  visible; ensure they never cover the hand or the memory gauge.
- Board-mode selection rail (1.2/1.5): on mobile the left rail becomes a
  bottom sheet above the hand.
- Showcases and combat scenes (Phases 2–3): center-stage card scales to
  viewport (max-height driven), shield-break and clash effects stay inside
  safe areas (notches — use `env(safe-area-inset-*)`).
- Drag intent labels (4.1): touch drag parity — labels must not sit under
  the finger; offset above the touch point.
- Turn control button (4.2) and memory gauge: minimum touch target 44px;
  gauge cells stay legible at 390px width (allow horizontal compression per
  the existing landscape tuning).
- Hand fan (`boardPieces.tsx` `handOverlap`): re-derive constants per
  breakpoint if new chrome changed available height.
- Text scaling: no clipped effect text in notices/tooltips at small widths;
  line-clamp with expand-on-tap where needed.

Method: drive the real app (bot match) at each viewport via browser
automation, screenshot every flow, fix in `game.css`/component CSS with
media queries and container-relative sizing, re-verify. Add any purely
numeric layout helpers to `timings.ts`-style modules with tests where logic
(not CSS) decides layout.

## Testing

- Pure modules (`animationQueue`, `sidePanels`, `timings`, presentation
  selectors) get colocated Vitest suites.
- `uiCompleteness.test.ts` stays green throughout.
- Manual matrix per slice: bot match on desktop + landscape phone, reduced
  motion on/off, reconnect mid-sequence (no ghost animations), spectator of
  both seats.
- `dev/BoardShowcase.tsx` gains showcase entries for each new sequence so
  animations iterate without a live match.
- Visual confirmation: implementing agents use the Orca embedded browser
  (`orca goto/snapshot/screenshot/click --json`; load the guide with
  `orca skills get orca-cli`) against the local dev server to verify each
  sequence and capture screenshots per slice. If Orca is unavailable in the
  session, tests/typecheck/build still gate and the visual pass is deferred
  to the responsiveness slice.

## Risks

- Sequencer regressions on reconnect replay — mitigate by porting
  `cueBaselineRef` behavior into the queue with a dedicated test.
- Opponent-decision visibility (1.6) may need a small server event — confirm
  before building; keep it seat-scoped to avoid leaking hidden info.
- Summoning-sickness flag (3.2) may need a schema addition — verify first.
- `GameScreen.tsx` churn conflicts with parallel card-audit work — keep
  refactors mechanical and land slice 1 quickly.
- `motion` adds ~30 kB gzip to the client bundle — acceptable; confirm no
  double-animation where a `battle-*` keyframe and a motion variant target
  the same element.
